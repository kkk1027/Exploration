# P7 · V2 通道治理验证报告

> 日期：2026-10-24
> 目标：把"候选生成质量"问题里**不用重做算法就能防住**的那部分先防住，并用 10 轮
> 同口径验收证明它确实防住了；防不住的明确写进下一阶段。
> 对照组一律是 V0（`cand1..10`，同样 120 s 探索、同视觉配置、同随机起点策略）。

---

## 0. 一句话结论

V2-①②**达到了它的设计目标**（manager 绕过仲裁自采样 27% → **1%**，卡死 12 → 9 次），
但过程中暴露出一个**更靠前的、跨所有组共有的零容错缺陷**（返航兜底把 manager 的
3 次重试预算每轮吃满），V2 把探索推深推远后被它吃掉 4 轮返航。
该缺陷已修（`session_driver` 兜底加"车确实没动"前置条件），2 轮预验证 0 次误取消，
10 轮复验见第 6 节。

**教训**：A/B 里出现"新功能组变差"时，先把失败**归因到机制**再决定回退——
这次回退 V2 是错的，真正该修的是那条老兜底。

## 1. V2-① 通道窗口：让仲裁先说话

| 项 | 内容 |
| --- | --- |
| 问题 | manager 自带的 fallback 采样（`source=exploration_manager`）**完全绕过仲裁**，占 V0 派发的 27%，且实测卡死里 62% 出自这条路径 |
| 手段 | `rrt_fallback_wait_sec`：manager 在自己采样前先等仲裁的合格候选 |
| 约束 | 该参数在车端 `__init__` 里一次性缓存，`ros2 param set` 无效 ⇒ 只能 launch 级注入 |
| 实现 | `harness/patch_car_launch.py --rrt-wait 12.0`，带哨兵注释 + journal，`--restore` 逐字节还原 |
| 实测生效 | `launch.log`：`RRT fallback wait=12.0s`；探索期 `waiting for RRT frontier before manager fallback` 出现 4~10 次/轮（V0 为 0） |

### 1.1 途中抓到的两个"静默失效"

1. **重复字典键覆盖**：车端 launch 里 `'rrt_fallback_wait_sec'` 在同一
   `parameters=[{...}]` 字典里出现两次（先 0.0 后又被我插入 12.0 的位置在它之前），
   Python 字典字面量是**后者覆盖前者** ⇒ 插进去的 12.0 被后面的 0.0 静默盖掉，
   表现是"注入成功、日志也打了、就是不生效"。
   改为**整行替换最后出现的那一处**（生效行），原行记进 journal、restore 时原样放回。
   逐字节可逆已实测：`71dfffdf… → 注入 → 71dfffdf…`。
2. **`occ_frac_r2` 从来没被返回**：`region_complexity()` 不返回该键，而
   `gate_adjusted_penalty()` 用 `f.get('occ_frac_r2', 0.0)` 取默认 0 ⇒ V1 的
   "复杂区软惩罚"一直是死代码（这也解释了 V1 里 `gate_penalized` 为什么几乎不动）。
   已补上，口径与离线分析脚本 `harness/analyze_candidates.py` 一致
   （2 m 窗口内净空 <0.30 m 的格占比）。

> 这两个都属于"看起来跑通了、其实没接上"的典型。现在 `param_audit.sh` 每轮直接核对
> 运行期 `rrt_fallback_wait_sec=12.0` / `return_home_orientation_grace_sec=22.0`。

## 4. 归因：4 轮返航失败到底是谁的锅

逐轮看返航重试的**消耗原因**（`retrying return-home N/3` 的前因）：

| 轮次 | 结论 | 1/3 | 2/3 | 3/3 | 消耗原因 |
| --- | --- | --- | --- | --- | --- |
| v2r1 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r2 | FAIL | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r3 | FAIL | ✓×2 | ✓×2 | ✓×2 | `front obstacle too close: 0.56m` + cancel ×2 |
| v2r4 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r5 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r6 | FAIL | ✓ | ✓ | — | `goal was canceled` ×2 |
| v2r7 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r8 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r9 | PASS | ✓ | ✓ | — | `goal was canceled` ×2 |
| v2r10 | FAIL | ✓ | ✓ | ✓ | `goal was canceled` ×3 |

**关键事实：V0 的 10 轮、V1 的 11 轮、V2 的 10 轮，每一轮都把
1/3→2/3→3/3 打满**，而且消耗原因几乎全是 `goal was canceled` ——
取消者不是 Nav2、不是 watchdog，而是**我们自己的 `session_driver`**。

### 4.1 机制

`session_driver` 阶段3 有一条兜底：

```python
if (self.return_home_ok is None and self.t_done_called is not None and ...):
    self._call_done()                     # 重发 set_mapping_done
    if self._retries >= 3 and self._cancel_sent < 3:
        self._cancel_all_goals()          # 取消 /navigate_to_pose 上的全部目标
```

它的**本意**是"等探索目标取消卡住时"清一次目标。但判据里只有
`return_home_ok is None`——它**不知道 manager 其实已经派出返航目标、车正在往回开**，
于是每轮都无条件重发并在第 3 次重发后 `cancel-all`，
把 manager 仅有的 3 次返航重试预算**全部吃满**。

预算一满就**零容错**：只要再出现任何一次干扰（如 `front obstacle too close`），
整轮返航必失败。V0 之所以 10/10 全绿，是因为它探索得近、返航起点离原点近，
零容错也够用；V2 把探索推深推远后，这条老缺陷就浮出水面。

v2r2 的 276 次底盘接触也是这条链的下游：goals 被反复取消、车在
`(3.7,-2.2)` 附近反复重试返航且越走越远（4.30→5.02 m），最后顶到墙上。

### 4.2 已修

`session_driver`：
- 里程计回调记录位置历史，新增 `_moved_recently(win=4 s, thr=0.06 m)`；
- 兜底前置条件加 `not self._moved_recently()`——"等活跃目标取消卡住"这个场景
  的定义就是**车不动**，车还在动就不该去掐目标；
- `cancel-all` 上限 3 → 2（预算只有 3 次，兜底不该把它耗尽）。

**2 轮预验证**（同 V2 配置）：

| 轮 | 结论 | cancel-all | 返航重试消耗 |
| --- | --- | --- | --- |
| fxr1 | PASS | 0 | 0/3 |
| fxr2 | PASS | 1 | 1/3 |

对照：修之前**每一轮**都是 3 次 cancel-all + 3/3 用满。

## 5. 这个方案防住了什么、防不住什么

### 防住了（有数据）
1. **manager 绕过仲裁自采样**：27% → 2%（通道确实关住了；但注意第 6.1 节：
   它只是"候选饥荒"的症状，关掉它本身并不能减少卡死）。
2. **"挑不出候选就什么都不派"**：改成派开阔观察点，17 次触发；
   与卡死/接触无相关性，但有一次接触轮次疑似被它送进远角 ⇒ 已收紧边界。
3. **闸门类软惩罚的死代码**：`occ_frac_r2` 补上后，V1 的复杂区惩罚才真的会生效
   （为后续重新启用 `gate_enabled` 做前提）。
4. **兜底取消的自伤**：返航重试预算从"每轮必打满"变成"基本不动"。

### 防不住（明确留到下一阶段）
1. **manager 在窗口之外仍然能自采样**：V2-① 是"让路"不是"关门"，manager 的
   fallback 采样逻辑本身没动；要关门得靠 V2-③ 后置 veto。
2. **车已经动起来之后才发现落点差**：闸门只看落点，管不了"路走到一半才发现是死胡同"。
   V2-③（订阅 `/plan`，对非自派目标做后置否决）就是补这一段。
3. **探索末段"停在哪"的质量**：4 轮返航失败的共同点是"探索结束时车停在角落/贴墙"，
   V2 只影响"派谁"，管不到"最后停在哪"。区域冷却 + `keepout.json` 属下一阶段。

## 6.1 一个必须写下来的负面发现：manager 绕过仲裁是**症状**，不是**原因**

V0 的归因结论是"卡死里 62% 出自 `source=exploration_manager`"，据此设计了 V2-①。
但把这条通道基本关掉之后（27% → 2%）：

| | V0 | V3 |
| --- | --- | --- |
| manager 派发 | 23（27%） | 1（2%） |
| 卡死次数 | 12 | 13 |

**卡死次数没有下降**。说明原来那条相关性是**因果反了**：
manager 之所以自己采样，是因为仲裁器当时**挑不出合格候选**
（`本轮候选全部被拒` 在 v2r2 里每 2 s 出现一次），
它是"候选饥荒"的**下游表现**，而不是卡死的原因。

这条修正很重要，它直接决定下一阶段该做什么：
- **不是**继续收紧通道（通道已经收干净了，收益见底）；
- **而是**候选生成本身——即用户最早那句"经常性接受复杂区域内候选造成卡死"，
  指的正是候选**质量**，V2-①② 从来没有碰过它。

## 6.2 为什么要重测基线

V0 的"10/10 全绿"是在**返航兜底每轮吃满重试预算**的前提下侥幸拿到的
（零容错、刚好够用）。兜底修好之后，V0 配置的基线本身需要重测，
否则后续所有 A/B 都在跟一个"运气基线"比。
→ `logs/round_*_b0r*` = **V0 配置（`RRT_WAIT=0`）+ 兜底修复**，作为新基线。

## 7. 三组十轮的正面对比与裁决

| 组 | 配置 | 全绿率 | 返航失败 | 接触 | 卡死 | 硬倒车 | manager 占比 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `cand` | V0 原基线（无修复） | **10/10** | 0/10 | 0/10 | 12 | 0 轮超限 | 27% |
| `b0r` | V0 + 兜底修复 + **V2-②** | 9/10 | **0/10** | 1/10 | 9 | 0 轮超限 | 30% |
| `v3r` | V0 + 兜底修复 + **V2-①②** | 8/10 | 1/10 | 1/10 | 13 | 多轮 0.19~0.74 m | **2%** |

（每组 10 轮 × 120 s 探索，同视觉、同随机起点策略、同验收判据；
唯一变量就是那两个开关。）

### 裁决 1：V2-① 有害，默认关闭

V2-① 把一个 90% 的基线打成 80%，多出 1 轮返航失败，并且**控制器硬倒车显著变多**
（`v3r` 多轮 0.19~0.74 m，`b0r` 多为 0.01~0.25 m）。

机制解释得通：manager 空等 12 s 期间**车是静止的**，仲裁接着把更深的 RRT 前沿派出去，
车被推进更窄的角落，只能靠 MPPI 硬倒车退出——这正好是 v3r10
（3 个硬倒车窗共 0.74 m、零接触）和 v3r7（2 次接触）的样子。

⇒ `harness/round.sh` 的 `RRT_WAIT` 默认改回 **0**（不注入），保留 `RRT_WAIT=12`
的注入能力以便复现实验。

### 裁决 2：V2-② 中性偏风险，收紧边界后保留

它确实把"什么都不派"补上了（17 次/轮组），但 `b0r10` 那 6 次接触正是发生在
"保底观察点把车送到 `(7.15,-3.9)`，随后又被 RRT 前沿推到 `(7.74,-4.9)`"的那一轮。

⇒ 收紧：最小可逃逸方向 **6/8**（原 5/8）、离车 **≤2.0 m**（原 3.0 m）、
单轮上限 **10 次**（原 30 次）。宁可不派，也不把车送到远角。

### 裁决 3：返航兜底修复是唯一无争议的净收益

返航失败 **4/10 → 1/10 → 0/10**（v2r → v3r → b0r），且没有任何副作用。
`cancel-all` 从"每轮 3 次"降到 0~1 次，manager 的 3 次返航重试预算基本不再被自己人吃掉。

## 8. 下一阶段该做什么（按证据排序）

1. **候选质量（真正的病根）**——用户最早那句"经常性接受复杂区域内候选造成卡死"
   指的就是这个，V2-①② 从头到尾没碰过它。具体：
   - `path_and_width()` 目前只用"最小宽度"一个标量描述整条路径，
     应升级为**路径代价场**（沿途窄段长度、视觉障碍拦截次数、需倒车概率）；
   - 把 `esc_dirs` / `occ_frac_r2` 这两条已在 V0/V1 数据里验证有区分度的规则
     正式接回闸门（`gate_enabled`），并先修好软惩罚（本轮已补 `occ_frac_r2`）。
2. **后置 veto（原 V2-③）**——管"车动起来之后才发现落点差"这一段。
   注意本次教训：**只在探索期生效，返航期必须完全禁用**（否则会重演
   "自己人 cancel 掉返航目标"的那类自伤）。
3. **硬倒车治理**——现在只有 `retreat` 机制受控（单窗 0.15 m / 每次会话 2 次），
   但**控制器自己倒车不受任何约束**（v3r10 三个硬倒车窗共 0.74 m）。
   需要把"控制器倒车 >0.15 m/窗"也纳入监测与限幅。
4. **区域冷却 + `keepout.json` 持久化**——把反复卡死的区域跨轮次记住。

本身并不会必然导致卡死，真正相关的是**候选/落点的质量**。

## 10. V2-③ 后置 veto：实现 + 十轮验收

### 10.1 它补的是哪一段

闸门（V1）只看**落点**，且只管**仲裁器自己派的**候选。manager 在窗口之外自己
采样时，那条路径上没有任何质量检查。V2-③ 换个位置看问题：不看谁派的，只看
**Nav2 真正在执行什么**——订阅 `/plan`，取末位点当"正在执行的目标"，
命中硬闸门就把它取消掉。

关键实现约束（都是踩过的坑）：

| 约束 | 原因 |
| --- | --- |
| 只取消当前 EXECUTING 的**那一个** `goal_id` | 绝不用 cancel-all —— P7 第 4 节那 4 轮返航失败就是 cancel-all 打出来的 |
| 只在探索期生效（`mapping_done=false` 且 `pending_home_goal` 空且 `return_home_retry_count=0`；没收到过 nav_state 也一律不动作） | 状态未知时去 cancel = 赌命 |
| 原点 0.8 m 内不碰 | 返航终点就在原点 |
| 每局 ≤2 次、30 s 冷却、同目标 20 s 不重复 | 否则会跟 manager 拉锯，把派发节奏打乱 |
| 自己 8 s 内派过的点不 veto | 自己派的已经过闸门，再否一次是自打自脸 |

### 10.2 十轮验收（`c1r` vs 基线 `n1r`）

| 指标 | n1r（基线） | **c1r（③ ON）** | 判读 |
| --- | --- | --- | --- |
| 全绿率 | 10/10 | 9/10 | 差 1 轮（见 11.3） |
| 返航失败 | 0/10 | 1/10 | 同上 |
| 物理接触 | 0/10 | **0/10** | = |
| 卡死次数 | 12 | 12 | = |
| manager 占比 | 35/64 = 55% | **32/74 = 43%** | ✓ 下降 |
| 仲裁器（rrt）派发 | 18（28%） | **31（42%）** | ✓ 接管 |
| veto 触发 | — | 1~2 次/轮（多数打满 2 次上限） | 功能生效 |

### 10.3 那 1 轮失败不是 veto 造成的

`c1r4` 的失败链：探索时间到 → manager 拒绝派返航 —— 日志原文
`return-home delayed: current pose is too close to occupied /map cells`，
3 次重试在 **6 秒内**耗尽 → 整轮判失败。

- 这不是 veto 后置拦截导致的：该轮只有 1 次 veto，发生在结束建图**前 67 s**，
  mapping_done 之后没有任何 veto（阶段闸生效）。
- 这是**已知的、跨历史的偶发模式**：在 272 轮历史数据里，
  这条 "too close to occupied" 出现在 **21 轮（7.7%）**。
- 车端的行为是"停得太贴障碍就拒绝返航，且只重试 3 次、每次 2 s"——
  它不会先挪开一点再试。

### 10.4 裁决：功能保留、默认关闭

按"任何退化立即回退该步"的纪律：`c1r` 有 1 轮返航失败（即便归因于既有模式），
**默认仍为 `veto:=false`**，实现与参数全部保留、可随时复现：

```bash
VETO=true bash harness/round.sh c1rX 120              # 复现 ③
GATE=true VETO=true bash harness/round.sh g2rX 120    # 复现 ③+闸门组合（第 12 节）
```

## 12.1 真正卡住 PASS 的不是撞障，而是"停在哪儿"

把近期所有失败轮摊开看，失败项高度集中在一处：

| 轮 | 失败项 | 车端原话 |
| --- | --- | --- |
| `c1r4` | return_home | `return-home delayed: current pose is too close to occupied /map cells` |
| `g2r2` | return_home | `front obstacle too close: 0.28m` → 3 次重试耗尽 |
| `g2r3` | return_home, contact | 同上叠加接触 |

共同机制：**探索时间到时车停在贴障位置**，车端 manager 拒绝启动返航，
而且只重试 3 次 × 2 s（6 秒内耗尽），它**不会先挪开一点再试**。
所以"探索结束那一刻车在哪"直接决定这一轮能否返航。

这条消息在 **272 轮历史数据里出现在 21 轮（7.7%）**，是既有的偶发模式；
而 gate/veto 会让"仲裁无候选"的时段变多，车更容易就地停住，把它的发生率抬高。

## 12.2 对策：探索末段"停车友好"偏置（已实现，验收见 12.3）

两条互相配合的改动，都不硬拒候选（避免把自己饿死）：

1. **末段加罚**：最后 `tail_park_sec=25 s` 内，对 `esc_dirs < 5` 或
   `2 m 障碍占比 ≥ 0.30` 的候选加 900 分罚（走 `gate_adjusted_penalty`
   同一条路径，v1/v2/v3 三个打分器全覆盖）→ 让车尽量停在空地；
2. **末段放宽保底**：同一窗口内把保底观察点门槛放宽到 `esc ≥ 3`、`≤2.5 m`、
   冷却 4 s，避免末段"干脆没有目标、就地停住"。

`harness/test_tail_park.py` 焊住 7 条边界（窗口内/外、开关、无进度信息、边界值），
已并入 smoke 第 6 组。

### 12.4 关于"返航起不来"这条失败模式的结论

把它在**所有组**里的出现次数摊开：

| 组 | 轮数 | 命中 "too close to occupied / front obstacle" 的轮 |
| --- | --- | --- |
| `cand`（V0 原始基线） | 10 | 0 |
| `n1r`（现默认） | 10 | 0 |
| `c1r`（③） | 10 | 1（c1r4） |
| `g2r`（③+闸门，提前中止） | 4 | 2 |
| `t1r`（末段偏置） | 10 | 2 |

10 轮样本里出现 0 次或 2 次都在噪声内 —— 也就是说：
**V0 的"10/10 全绿"本身自带约 45% 的运气成分**（(1-0.077)^10 ≈ 0.45）。

这条模式的真因在**车端**：manager 在"当前位置太贴障碍"时拒绝派返航，
只重试 3 次 × 2 s（6 秒耗尽），且**不会先挪开一点再试**。

≤0.8 m 安全 standoff 挪一步再重试"），这属于下一阶段（见第 15 节）。

1. **返航起不来时的"挪一步再重试"**（最高优先级；命中率 ~7%/轮，且在所有组都出现）

## 16. 返航前"接管点"兜底：实现、三次静默失效与十轮结果

### 16.1 为什么做它

第 12.4 节把"探索结束时停在贴障处 → 车端拒绝派返航 → 3 次重试 6 秒耗尽"
认定为最主要的残余失败模式（历史 272 轮命中 21 轮 = 7.7%）。

### 16.2 做法

在 `session_driver` 里、**调用 `set_mapping_done` 之前**插一步：

1. 触发判据：`front_blocked`，或 `front_min_range < 0.45`（对齐车端
   `front<0.45 → publish_zero_velocity` 的安全门限），地图净空 < 0.45 作为补充；
2. 方向选择：front/left/right 三向里挑最开阔的一侧，要求 ≥0.55 m；
   **rear 绝不用**（后向 110°~240° 是激光盲区，nav_state 给的是 99=无数据）；
3. 派一个 `NavigateToPose`（≤0.6 m），**朝向设为移动方向**；到位（≤0.35 m）或
   超时（8 s）后再结束建图；每局限 2 次。

放在 `set_mapping_done` 之前是关键：这样不消耗 manager 那 3 次返航重试预算。

### 16.3 过程中撞到的三次"静默失效"（都是写了没生效）

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | 接管点一次都没触发（s1r1） | 按 `/map` 判"贴障"**漏判**：那一轮地图净空够、车端却一直报 `front obstacle too close`。低矮障碍常常没画进 cartographer 的 `/map`（正是视觉融合要补的盲区）→ 改用车端 nav_state 自己的四向测距 |
| 2 | 改完还是走"地图选点"分支（k1r1） | 补丁按 `def _on_nav_state(self, m)` 替换，而真实参数名是 `msg` → replace **静默没生效**，`self.nav` 永远是空 dict。这是今天第二次同类事故（第一次是 `occ_frac_r2` 从没返回） |
| 3 | 车挪到位了，返航仍被拒（k1r1） | 只改位置不改朝向：车挪开了、车头照样顶着障碍。→ 接管点现在会朝移动方向摆头；到位阈值也从 0.25 放宽到 0.35（实测车停在 0.29 m 被判"超时放弃"） |
| 4 | `CORRIDOR_W=0.85` 实验里日志仍打"走廊 < 1.05m" | launch 里 `corridor_width` 只做了 `DeclareLaunchArgument`，**从来没映射到仲裁节点参数**（节点参数名是 `corridor_width_m`）→ 历史上所有 `CORRIDOR_W=*` 扫描都是空操作 |

四次事故里有三次是**同一类**：语法正确、跑得起来、日志正常，就是没起作用。
所以补两道静态闸：

- `harness/test_param_types.py` 反向检查"空旋钮"：每个 `DeclareLaunchArgument`
  必须在文件里被 `LaunchConfiguration` 引用过，否则 FAIL；
- `harness/test_driver_hooks.py` 把"写了但没接上"变成静态断言（nav_state 真的
`json.loads`、兜底真的受"车没动"约束、接管点真的走四向测距且不用 rear、
`region_complexity` 真的返回 `occ_frac_r2`、veto 真的只取消单个 goal_id）。
已自证：把 `rear` 放回候选列表，该测试立刻 FAIL。

### 16.4 十轮结果（`m1r`）

| 指标 | n1r（基线） | m1r（接管点 ON） |
| --- | --- | --- |
| 全绿率 | 10/10 | 8/10 |
| 返航失败 | 0/10 | 2/10 |
| 物理接触 | 0/10 | 1/10（m1r9，326 次） |
| 卡死次数 | 12 | 19 |

**但要看清楚这两轮失败是什么**：

- `m1r3`：接管点**正确触发**（`front_blocked` → 挪向 left，range 0.68 m），
  可是 `planner_server: failed to create plan, no valid path found` ——
  车卡在一个**连 0.4 m 都规划不出路**的死口袋里，Nav2 挪不动它。
  这一轮换成任何接管点都救不了。
- `m1r9`：Nav2 在死口袋里跑 **Spin 恢复行为**（原地转 1.57 rad），转的过程中
  车体扫到障碍 → 326 次接触。这是车端恢复行为在窄处的固有风险，与接管点无关。

十轮里接管点只触发 1 次，**当前样本还证明不了它的收益**（那只 7.7% 的枪这次
没打到、打到的那次又是死口袋）。按"保守优先"的口径它保留 ON——它只在
"车已经被判定贴障、否则这一轮必然失败"的场合才动作，代价只是那个场合的 8 秒。

### 16.5 结论：这条模式的真因在候选质量

"死口袋"是**候选质量**问题：车被送到了 Nav2 连 0.4 m 都规划不出的地方。
无论返航前怎么挪，都治不了根。这正好指向下一阶段唯一还没做的那条（第 15 节第 2 条）：
把 `path_and_width()` 从"最小宽度一个标量"升级成**路径代价场**，
在派发前就避开"进去容易出来难"的区域。

| 规划失败 | 47（4/轮） | 32（6/轮） |
| 候选全灭 | 878（82/轮） | 418（84/轮） |

**放宽走廊并没有解决"候选全灭"**（84/轮 vs 82/轮，没动），却把接触和返航失败
带上来了 —— 因为被放行的正是"更窄的缝"，车开进去就更难出来。

### 17.3 这条实验真正的收获

1. **"候选全灭"主要不是走廊阈值造成的**：放宽 20% 只让数字从 82 变成 84/轮。
   拒绝量的大头在 `rejected_size`（未知格不足）与 `rejected_path`（不可达），
   以及黑名单累积 —— 也就是说候选**数量**本身就不够，不是筛得太狠。
2. 因此下一步不该继续调阈值，而该提高**候选生成**本身
   （更密的前沿采样 / 更好的前沿聚类），以及把"进去容易出来难"的落点
   在派发前就判掉（路径代价场）。

## 21. 针对"静止卡死"的两条车端旋钮（都试过，都不采纳）

### 21.1 front_stop_distance 0.65 → 0.50（可回退 launch 注入）

静止卡死的触发线就在车端：`front_min_range < front_stop_distance`（原厂 0.65）
连续 5 拍 → `front_blocked` → `publish_zero_velocity`，而 Nav2 仍显示
`executing`，看门狗 5 s 后才介入。所以把这条线放宽（0.65 → 0.50）本该直接
减少卡死次数。

`patch_car_launch.py` 增加 `--front-stop`（整行替换 + journal + 逐字节还原，
md5 往返一致），round.sh 用 `FRONT_STOP=0.50` 传，param_audit 核对运行期值。

十轮结果（`fs1r`）：

| 指标 | mc1r（0.65） | **fs1r（0.50）** |
| --- | --- | --- |
| 全绿率 | 10/10 | 9/10 |
| 返航失败 | 0 | 1 |
| 物理接触 | 0 | 0 |
| 静止超时 | 13（1.3/轮） | **11（1.1/轮）** |
| manager 占比 | 41% | 31% |

**裁决：不采纳。** 卡死只降了 15%（13→11），仍在噪声带内，却多出 1 轮返航失败
（`return-home goal was canceled` 两次）。按"任何退化立即回退"，`FRONT_STOP`
默认保持 0（不注入）。

### 21.2 接管点触发阈值 0.45 → 0.70（对齐车端 0.65）

动机：车端真正拒派返航的线是 `front_stop_distance=0.65`，而我们原来把接管点
触发设成 0.45，等于"车已经贴住了才想挪"。十轮（`sd1r`）：**8/10、2 轮返航失败**，
两轮失败都是返航**途中** front 掉到 0.35~0.38 m —— 而接管点只在"探索截止那一刻"
动作，根本管不到这段。

**裁决：回退到 0.45。** 结论也记下来了：这一档失败模式的根治在车端
（返航途中的 front 判据），harness 侧不做越权干预。
