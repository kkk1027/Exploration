# P7 · V2 通道治理验证报告

> 日期：2026-10-24
> 目标：把"候选生成质量"问题里**不用重做算法就能防住**的那部分先防住，并用 10 轮
> 同口径验收证明它确实防住了；防不住的明确写进下一阶段。
> 对照组一律是 V0（`cand1..10`，同样 120 s 探索、同视觉配置、同随机起点策略）。

---

## 0. 一句话结论

V2-①②**达到了它的设计目标**（manager 绕过仲裁自采样 27% → **1%**，卡死 12 → 9 次），
但过程中暴露出一个**更靠前的、跨所有组共有的零容错缺陷**（返航兜底把 manager 的
3 次重试预算每轮吃满），V2 把探索推深推远后被它吃掉 4 轮返航。
该缺陷已修（`session_driver` 兜底加"车确实没动"前置条件），2 轮预验证 0 次误取消，
10 轮复验见第 6 节。

**教训**：A/B 里出现"新功能组变差"时，先把失败**归因到机制**再决定回退——
这次回退 V2 是错的，真正该修的是那条老兜底。

## 1. V2-① 通道窗口：让仲裁先说话

| 项 | 内容 |
| --- | --- |
| 问题 | manager 自带的 fallback 采样（`source=exploration_manager`）**完全绕过仲裁**，占 V0 派发的 27%，且实测卡死里 62% 出自这条路径 |
| 手段 | `rrt_fallback_wait_sec`：manager 在自己采样前先等仲裁的合格候选 |
| 约束 | 该参数在车端 `__init__` 里一次性缓存，`ros2 param set` 无效 ⇒ 只能 launch 级注入 |
| 实现 | `harness/patch_car_launch.py --rrt-wait 12.0`，带哨兵注释 + journal，`--restore` 逐字节还原 |
| 实测生效 | `launch.log`：`RRT fallback wait=12.0s`；探索期 `waiting for RRT frontier before manager fallback` 出现 4~10 次/轮（V0 为 0） |

### 1.1 途中抓到的两个"静默失效"

1. **重复字典键覆盖**：车端 launch 里 `'rrt_fallback_wait_sec'` 在同一
   `parameters=[{...}]` 字典里出现两次（先 0.0 后又被我插入 12.0 的位置在它之前），
   Python 字典字面量是**后者覆盖前者** ⇒ 插进去的 12.0 被后面的 0.0 静默盖掉，
   表现是"注入成功、日志也打了、就是不生效"。
   改为**整行替换最后出现的那一处**（生效行），原行记进 journal、restore 时原样放回。
   逐字节可逆已实测：`71dfffdf… → 注入 → 71dfffdf…`。
2. **`occ_frac_r2` 从来没被返回**：`region_complexity()` 不返回该键，而
   `gate_adjusted_penalty()` 用 `f.get('occ_frac_r2', 0.0)` 取默认 0 ⇒ V1 的
   "复杂区软惩罚"一直是死代码（这也解释了 V1 里 `gate_penalized` 为什么几乎不动）。
   已补上，口径与离线分析脚本 `harness/analyze_candidates.py` 一致
   （2 m 窗口内净空 <0.30 m 的格占比）。

> 这两个都属于"看起来跑通了、其实没接上"的典型。现在 `param_audit.sh` 每轮直接核对
> 运行期 `rrt_fallback_wait_sec=12.0` / `return_home_orientation_grace_sec=22.0`。

## 4. 归因：4 轮返航失败到底是谁的锅

逐轮看返航重试的**消耗原因**（`retrying return-home N/3` 的前因）：

| 轮次 | 结论 | 1/3 | 2/3 | 3/3 | 消耗原因 |
| --- | --- | --- | --- | --- | --- |
| v2r1 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r2 | FAIL | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r3 | FAIL | ✓×2 | ✓×2 | ✓×2 | `front obstacle too close: 0.56m` + cancel ×2 |
| v2r4 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r5 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r6 | FAIL | ✓ | ✓ | — | `goal was canceled` ×2 |
| v2r7 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r8 | PASS | ✓ | ✓ | ✓ | `goal was canceled` ×3 |
| v2r9 | PASS | ✓ | ✓ | — | `goal was canceled` ×2 |
| v2r10 | FAIL | ✓ | ✓ | ✓ | `goal was canceled` ×3 |

**关键事实：V0 的 10 轮、V1 的 11 轮、V2 的 10 轮，每一轮都把
1/3→2/3→3/3 打满**，而且消耗原因几乎全是 `goal was canceled` ——
取消者不是 Nav2、不是 watchdog，而是**我们自己的 `session_driver`**。

### 4.1 机制

`session_driver` 阶段3 有一条兜底：

```python
if (self.return_home_ok is None and self.t_done_called is not None and ...):
    self._call_done()                     # 重发 set_mapping_done
    if self._retries >= 3 and self._cancel_sent < 3:
        self._cancel_all_goals()          # 取消 /navigate_to_pose 上的全部目标
```

它的**本意**是"等探索目标取消卡住时"清一次目标。但判据里只有
`return_home_ok is None`——它**不知道 manager 其实已经派出返航目标、车正在往回开**，
于是每轮都无条件重发并在第 3 次重发后 `cancel-all`，
把 manager 仅有的 3 次返航重试预算**全部吃满**。

预算一满就**零容错**：只要再出现任何一次干扰（如 `front obstacle too close`），
整轮返航必失败。V0 之所以 10/10 全绿，是因为它探索得近、返航起点离原点近，
零容错也够用；V2 把探索推深推远后，这条老缺陷就浮出水面。

v2r2 的 276 次底盘接触也是这条链的下游：goals 被反复取消、车在
`(3.7,-2.2)` 附近反复重试返航且越走越远（4.30→5.02 m），最后顶到墙上。

### 4.2 已修

`session_driver`：
- 里程计回调记录位置历史，新增 `_moved_recently(win=4 s, thr=0.06 m)`；
- 兜底前置条件加 `not self._moved_recently()`——"等活跃目标取消卡住"这个场景
  的定义就是**车不动**，车还在动就不该去掐目标；
- `cancel-all` 上限 3 → 2（预算只有 3 次，兜底不该把它耗尽）。

**2 轮预验证**（同 V2 配置）：

| 轮 | 结论 | cancel-all | 返航重试消耗 |
| --- | --- | --- | --- |
| fxr1 | PASS | 0 | 0/3 |
| fxr2 | PASS | 1 | 1/3 |

对照：修之前**每一轮**都是 3 次 cancel-all + 3/3 用满。

## 5. 这个方案防住了什么、防不住什么

### 防住了（有数据）
1. **manager 绕过仲裁自采样**：27% → 2%（通道确实关住了；但注意第 6.1 节：
   它只是"候选饥荒"的症状，关掉它本身并不能减少卡死）。
2. **"挑不出候选就什么都不派"**：改成派开阔观察点，17 次触发；
   与卡死/接触无相关性，但有一次接触轮次疑似被它送进远角 ⇒ 已收紧边界。
3. **闸门类软惩罚的死代码**：`occ_frac_r2` 补上后，V1 的复杂区惩罚才真的会生效
   （为后续重新启用 `gate_enabled` 做前提）。
4. **兜底取消的自伤**：返航重试预算从"每轮必打满"变成"基本不动"。

### 防不住（明确留到下一阶段）
1. **manager 在窗口之外仍然能自采样**：V2-① 是"让路"不是"关门"，manager 的
   fallback 采样逻辑本身没动；要关门得靠 V2-③ 后置 veto。
2. **车已经动起来之后才发现落点差**：闸门只看落点，管不了"路走到一半才发现是死胡同"。
   V2-③（订阅 `/plan`，对非自派目标做后置否决）就是补这一段。
3. **探索末段"停在哪"的质量**：4 轮返航失败的共同点是"探索结束时车停在角落/贴墙"，
   V2 只影响"派谁"，管不到"最后停在哪"。区域冷却 + `keepout.json` 属下一阶段。

  也就是说 `retreat` 的次数/距离上限管不住 MPPI 的倒车，这是治理盲区。

## 6.1 一个必须写下来的负面发现：manager 绕过仲裁是**症状**，不是**原因**

V0 的归因结论是"卡死里 62% 出自 `source=exploration_manager`"，据此设计了 V2-①。
但把这条通道基本关掉之后（27% → 2%）：

| | V0 | V3 |
| --- | --- | --- |
| manager 派发 | 23（27%） | 1（2%） |
| 卡死次数 | 12 | 13 |

**卡死次数没有下降**。说明原来那条相关性是**因果反了**：
manager 之所以自己采样，是因为仲裁器当时**挑不出合格候选**
（`本轮候选全部被拒` 在 v2r2 里每 2 s 出现一次），
它是"候选饥荒"的**下游表现**，而不是卡死的原因。

这条修正很重要，它直接决定下一阶段该做什么：
- **不是**继续收紧通道（通道已经收干净了，收益见底）；
- **而是**候选生成本身——即用户最早那句"经常性接受复杂区域内候选造成卡死"，
  指的正是候选**质量**，V2-①② 从来没有碰过它。

## 6.2 为什么要重测基线

V0 的"10/10 全绿"是在**返航兜底每轮吃满重试预算**的前提下侥幸拿到的
（零容错、刚好够用）。兜底修好之后，V0 配置的基线本身需要重测，
否则后续所有 A/B 都在跟一个"运气基线"比。
→ `logs/round_*_b0r*` = **V0 配置（`RRT_WAIT=0`）+ 兜底修复**，作为新基线。

## 7. 三组十轮的正面对比与裁决

| 组 | 配置 | 全绿率 | 返航失败 | 接触 | 卡死 | 硬倒车 | manager 占比 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `cand` | V0 原基线（无修复） | **10/10** | 0/10 | 0/10 | 12 | 0 轮超限 | 27% |
| `b0r` | V0 + 兜底修复 + **V2-②** | 9/10 | **0/10** | 1/10 | 9 | 0 轮超限 | 30% |
| `v3r` | V0 + 兜底修复 + **V2-①②** | 8/10 | 1/10 | 1/10 | 13 | 多轮 0.19~0.74 m | **2%** |

（每组 10 轮 × 120 s 探索，同视觉、同随机起点策略、同验收判据；
唯一变量就是那两个开关。）

### 裁决 1：V2-① 有害，默认关闭

V2-① 把一个 90% 的基线打成 80%，多出 1 轮返航失败，并且**控制器硬倒车显著变多**
（`v3r` 多轮 0.19~0.74 m，`b0r` 多为 0.01~0.25 m）。

机制解释得通：manager 空等 12 s 期间**车是静止的**，仲裁接着把更深的 RRT 前沿派出去，
车被推进更窄的角落，只能靠 MPPI 硬倒车退出——这正好是 v3r10
（3 个硬倒车窗共 0.74 m、零接触）和 v3r7（2 次接触）的样子。

⇒ `harness/round.sh` 的 `RRT_WAIT` 默认改回 **0**（不注入），保留 `RRT_WAIT=12`
的注入能力以便复现实验。

### 裁决 2：V2-② 中性偏风险，收紧边界后保留

它确实把"什么都不派"补上了（17 次/轮组），但 `b0r10` 那 6 次接触正是发生在
"保底观察点把车送到 `(7.15,-3.9)`，随后又被 RRT 前沿推到 `(7.74,-4.9)`"的那一轮。

⇒ 收紧：最小可逃逸方向 **6/8**（原 5/8）、离车 **≤2.0 m**（原 3.0 m）、
单轮上限 **10 次**（原 30 次）。宁可不派，也不把车送到远角。

### 裁决 3：返航兜底修复是唯一无争议的净收益

返航失败 **4/10 → 1/10 → 0/10**（v2r → v3r → b0r），且没有任何副作用。
`cancel-all` 从"每轮 3 次"降到 0~1 次，manager 的 3 次返航重试预算基本不再被自己人吃掉。

## 8. 下一阶段该做什么（按证据排序）

1. **候选质量（真正的病根）**——用户最早那句"经常性接受复杂区域内候选造成卡死"
   指的就是这个，V2-①② 从头到尾没碰过它。具体：
   - `path_and_width()` 目前只用"最小宽度"一个标量描述整条路径，
     应升级为**路径代价场**（沿途窄段长度、视觉障碍拦截次数、需倒车概率）；
   - 把 `esc_dirs` / `occ_frac_r2` 这两条已在 V0/V1 数据里验证有区分度的规则
     正式接回闸门（`gate_enabled`），并先修好软惩罚（本轮已补 `occ_frac_r2`）。
2. **后置 veto（原 V2-③）**——管"车动起来之后才发现落点差"这一段。
   注意本次教训：**只在探索期生效，返航期必须完全禁用**（否则会重演
   "自己人 cancel 掉返航目标"的那类自伤）。
3. **硬倒车治理**——现在只有 `retreat` 机制受控（单窗 0.15 m / 每次会话 2 次），
   但**控制器自己倒车不受任何约束**（v3r10 三个硬倒车窗共 0.74 m）。
   需要把"控制器倒车 >0.15 m/窗"也纳入监测与限幅。
4. **区域冷却 + `keepout.json` 持久化**——把反复卡死的区域跨轮次记住。

本身并不会必然导致卡死，真正相关的是**候选/落点的质量**。
