# P13 基线 · 候选派发质量与脱困能力

*冻结时间：2026-11-09*
*数据源：`/home/kbf/stemm_exploration_sim_ws/logs/round_20261109-1*`（16 轮）*
*生成工具：`harness/analyze_dispatch_risk.py`（只读，不启停任何 ROS/Gazebo 进程）*

---

## 0. 为什么要做这份基线

用户诉求有两条，且都"从头到尾没有好转"：

1. 小车的**脱困能力太弱**；
2. 经常被**派发难以脱困的候选**。

在动手加评分项之前，必须先有一把尺子能回答"派发出去了，然后呢？"。现有两套工具都答不了：

| 工具 | 回答的问题 |
|---|---|
| `harness/candidate_metrics.py` | 这一轮跑得合不合格（PASS/接触/覆盖） |
| `harness/analyze_candidates.py` | 落点在地图上的复杂度 |
| **`harness/analyze_dispatch_risk.py`（本文件配套）** | **派出去的目标为什么被取消 / 为什么"看起来成功"** |

---

## 1. 口径定义（读后续数字前必须知道）

| 概念 | 定义 |
|---|---|
| 派发（disp） | `navigation goal dispatched` 行；同一目标 3 s 内重复派发只计一次 |
| 终态配对 | 按目标坐标（±0.06 m）配对 `reached / canceled / failed`，时窗 90 s |
| **幻影成功（phantom）** | `reached` 但**隐含速度 > 1.5 m/s**（车最快 ≈0.5 m/s）且距离 ≥1 m → 物理不可能 |
| 真实到达（real） | `reached` 且非幻影 |
| 取消率 | `canceled / (real + canceled + failed)`，**分母剔除幻影** |
| 评分覆盖率 | `merge_validated / (merge_validated + merge_raw)`，即多少候选供给经过仲裁器评分 |

> 幻影成功必须从取消率分母里剔除。首版没剔除时出现"转角 >150° 取消率只有 6%"的**反向假结论** —— 因为远端目标大量被瞬时"成功"，根本没机会被取消。

## 2. 核心发现（三个，按严重程度排序）

### 2.1 【最严重】79% 的"到达"是幻影成功，机器人根本没动

| 项 | 值 |
|---|---|
| 已配对派发 | 286 |
| `reached` | 226 |
| 其中**幻影** | **179（79.2%）** |
| 真实到达 | 47 |

直接证据（`round_20261109-151947_v2r1r1/launch.log:733-742`）：

```
[bt_navigator]      Begin navigating from current location (5.55, -0.75) to (2.43, 3.73)
[controller_server] Received a goal, begin computing control effort.     ← .5357
[controller_server] Reached the goal!                                    ← .5662  (30 ms)
[bt_navigator]      Goal succeeded
[manager]           navigation goal reached; goal=(2.43, 3.73),
                    current=(5.55, -0.75), error=(xy=5.456m, ...)
```

**5.456 m 的目标在 30 ms 内"到达"**。此后该轮每一次派发都是这个模式，`current` 冻结在 `(5.55, -0.75)`，而 `(5.57, -0.66)` 正是同轮 148 s 卡死事件的坐标。

**机制**（`goal_checker` 配置，两份参数文件都是）：

```yaml
goal_checker:
  plugin: "nav2_controller::SimpleGoalChecker"
  xy_goal_tolerance: 0.15
  yaw_goal_tolerance: 0.25
  stateful: True          # ← 锁存成功后不自动复位
```

`SimpleGoalChecker` 在 `stateful: true` 下命中一次后 `isGoalReached()` 立即返回 `true`。
配合 P12 的 inplace 原地改目标（`GoalUpdater` 把 `{goal}` 改成更近的点），
控制器到达纠偏点即判成功并**锁存**，于是后续每个新目标都瞬间"成功"：
manager 认为一切正常 → 不重试、不取消、不交脱困 → 车一直停在原地 →
只有 `escape_supervisor` 的 40 s 累计计时最终以 `giveup_40s` 收场。

**相关性对照**（16 轮）：

| 组 | inplace 纠偏次数 | 幻影成功 |
|---|---|---|
| `offv2*` 5 轮 | 0 | **0** |
| `v2*` 5 轮 | 各 1 | 42 / 9 / 17 / 57 / 46 |
| `ix*` 6 轮 | 0 或 1 | 0（4 轮）/ 8（1 轮） |

`inplace=0 → phantom=0` 成立；但 `inplace=1` 不必然产生幻影（早期 `ixb1r1` 为 0），
说明还需 `GoalUpdater` 的 stamp 比较真的放行一次更新才会进入锁存态。

> 结论：**这是一条与候选评分完全无关的独立故障链**，但它污染了所有基于"到达率"的指标。
> 在它修好之前，任何候选评分的 A/B 都测不出真实效果。

### 2.2 派发距离是唯一与取消率干净单调相关的特征

剔除幻影后按派发距离分桶（16 轮，n=286，其中有效 107）：

| 派发距离 | n | 幻影 | 取消 | **取消率** |
|---|---|---|---|---|
| <3 m | 34 | 8 | 5 | **19%** |
| 3–4 m | 24 | 13 | 5 | **45%** |
| 4–6 m | 128 | 93 | 21 | **60%** |
| >6 m | 103 | 67 | 29 | **81%** |

**单调、跨度 4.3 倍。** 这是 P13-1 里 `w_dist` 权重最高的依据。

全局分布（297 次派发）：中位 **5.32 m**，p90 **9.21 m**，max 16.70 m；
**>4 m 占 79.8%**、**>6 m 占 35.0%**。

### 2.3 一半以上的候选供给绕过了仲裁器评分

| 项 | 值 |
|---|---|
| 16 轮评分覆盖率（`validated/(validated+raw)`） | **22.2% ~ 59.5%，中位 ≈ 37%** |
| 派发来源 | `exploration_rrt` 177、`exploration_manager` 106、`home` 14 |
| 能配对到 `candidate_probe.jsonl` 的派发 | 16 / 297 = **5.4%** |

`exploration_rrt` 与 `exploration_manager` 都是 manager 侧来源，其中 `exploration_rrt`
是 `/merged_frontier_goal`（仲裁合格目标 + RRT 原始目标混合），日志**无法区分**。
`frontier_merge` 的计数才是真相：每轮 `merge_raw` 与 `merge_validated` 相当，
即约**六成候选未经任何评分**直接派发。

## 3. 其余特征：证据不足，只能当次序项

剔除幻影后各桶有效样本很小（19~55），且 **271/297 条的特征来自"本轮最终地图"
而非派发时刻地图**（`candidate_probe` 配对率仅 5.4%），已知面积偏大、
`esc_dirs`/`comp_r2` 系统性偏乐观。

| 特征 | 分桶取消率 | 判断 |
|---|---|---|
| 转角 | <45° 44% / 45–90° 68% / 90–150° 81% / >150° 43% | **非单调**，>150° 桶有效样本仅 14 → 不作主项 |
| `esc_dirs` | ≤2 61% / 3–4 50% / 5–6 36% / 7–8 83% | 非单调，且特征源偏乐观 → 只作次序项 |
| `comp_r2` | ≤400 61% / 1201–3000 68% / >3000 49% | 弱；死口袋方向正确但跨度小 |
| 路径最小净宽 | 0.90–1.00 m 33% / 1.00–1.30 m 75% | 样本 3~11，**无统计意义** |

> 因此 P13-1 的设计原则是：**距离项给足权重，其余各项只作低权重次序项**，
> 并由 A/B 决定是否提权，而不是一上来就按"看起来合理"配权重。

## 4. 取消率基线（这是要改善的那个数）

| 组 | 派发 | 真实到达 | 取消 | 未配对 | **取消率** |
|---|---|---|---|---|---|
| `offv2*`（inplace OFF，无幻影） | 44 | 16 | 25 | 3 | **64%** |
| `v2*`（inplace ON，幻影主导） | 194 | 12 | 5 | 6 | —（样本被幻影吞掉） |
| 全部 16 轮 | 297 | 47 | 60 | 11 | 21%（含幻影稀释，仅供参考） |

**在没有幻影干扰的那 5 轮里，64% 的派发会被取消** —— 这正是用户说的
"候选生成后中途被无故打断"。

## 5. 与"脱困能力弱"的关系

`escape_supervisor` 的实测表现（同批日志 `supervisor.jsonl`）：

| 轮 | `unit_start` | `giveup_40s` |
|---|---|---|
| `v2r1`–`v2r5` | **0 / 0 / 0 / 0 / 0** | 2 / 1 / 1 / 2 / 2 |
| `offv2r4` | 4 | 1 |

即：**40 s 累计计时耗尽、一次脱困单元都没起过**。机制是幻影成功链的下游后果——
`maybe_arm()` 要求 `nav_busy or blocked_state`，而幻影循环里目标 30 ms 就结束，
`nav_busy` 长期为 `False`，`explore_watchdog` 又在 5 s 时 `cancel-all`，
于是永远凑不齐起单元的条件。

所以"脱困弱"不是脱困算法本身的问题，而是**上游让车"看起来在正常工作"**。

## 7. 对后续改动的约束（由本基线直接推出）

1. **先修幻影成功再看别的**：`stateful: True → False` 是一行改动，但它决定了
   后面所有指标是否可信。修之前不要用"到达率/成功率"做任何验收。
2. **距离项必须进评分**：4.3 倍单调跨度，是当前唯一统计显著的物理特征。
3. **其余特征只作次序项**，权重由 A/B 决定；不要因为"理论上应该重要"就配大权重。
4. **必须补评分覆盖率**：`validated` 只占六成，剩下四成完全不看风险。
5. **验收指标必须是"真实到达 / 取消率 / 幻影率"三件套**，
   单看"派发成功率"会被幻影喂到 55/56，毫无意义。
