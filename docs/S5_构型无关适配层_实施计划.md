# S5 实施计划：构型无关的可通行性适配层 + 几何分解区域调度

> **文档性质**：交接给实施智能体的施工图。本文档**不含任何未实测的数字**，
> 引用的数字全部来自本仓库已有文档，并标注出处。
>
> **上游决策**（用户 2026-11-13 已确认）：
> 1. 构型范围 = **差速 + 全向（麦轮/舵轮/四轮滑移）+ 阿克曼**；
> 2. 改动边界 = **仿真侧自由实现，车端仅允许 launch 级参数注入**（车端源码零提交，
>    patch 必须逐字节可还原）；
> 3. 复用原则 = 只借"可泛化、不依赖硬件"的部分，**不引入商用扫地机的单体轻量栈**。
>
> **本文档的非目标**（写进来是为了防止实施时跑偏）：
> 本仓库做的是**消费级算法落地的应用开发**，不是算法研究。因此
> "提出更优的收益函数"不是目标，"让同一套逻辑在不同构型/不同规模场景下都不崩"才是目标。

全部以**这一台两轮差速小车**为隐含前提硬编码在代码与 launch 默认值里。表现为：

| 位置 | 现值 | 隐含假设 |
|---|---|---|
| `pass_width_m` | `0.90` | 车宽 0.47 + 两侧各 0.215（launch 注释原文） |
| `narrow_floor_m` | `0.58` | 车宽 **0.40** + 两侧各 0.09（launch 注释原文） |
| `corridor_hard_m` | `0.92`（旧硬门，已被 S3 降级） | 同上 |
| `footprint` | `[[-0.18,±0.235],[0.32,±0.235]]` | 差速底盘，能原地转 |
| 转角门 | 75°（仲裁）/ 80°（manager） | **能原地旋转** |
| 脱困 | 旋转 + 前进，禁止后退 | 移动底盘，两侧无障碍 |

**已经在仓库里被记录的口径不一致（实施时必须先解决）**：

  两个阈值建立在相差 7 cm 的车体宽度上；
- `collision_probe` 的车体外接圆取 `hypot(0.29, 0.23) = 0.370 m`（底盘+轮），

  两者来自不同口径，**没有任何文档说明为何不同**。

⇒ 只要换一台车，这套阈值就必须整体重推；而重推时无从判断哪个口径是对的。
**这就是"通用性"真正的短板，也是本计划要消除的东西。**

### ⚠️ 优先级调整（2026-11-14，基于实测）

原计划的工程投放在**②上占约 70%**（M3 + Step 3 + Step 4），
而 2026-11-14 的实测与历史数据表明这个分配是错的。调整如下：

| 优先级 | 内容 | 原计划地位 | 调整后 | 依据 |
|---|---|---|---|---|
| **P0** | **框架策略 A/B 补完**（`frame_far_first`） | **完全不在这份计划里** | 最先做 | 它是 S5 所有基线的**口径前提**：S5 已跑的 22 轮**全部** `frame_first=false`，测的不是用户设计的策略 |
| **P1** | M4b 弓字形覆盖基线 | **完全没有** | 第二步做 | 用户原话：若能打平 frontier 探索，正好支撑"瓶颈不在选点策略"；零风险（不碰 `frontier_arbiter`） |
| **P2** | M4 NCR 真做终止判据 | Step 5，**只告警**，自动结束"留作后续单独立项" | 提升 | `no_frontier` 提前收敛是直接病根，而 NCR 公式已定义好 |
| **P3** | M3/Step 3 区域图 | **占篇幅最大** | **降级：改为嵌入框架阶段，算法换开运算** | 见下"与既有策略的冲突" |
| — | Step 4 区域级排序 | 原为"主路径 A/B" | 依赖 P3 | 原方案的 $1/(1+d)$ 近者优先与框架阶段的"越远越优先"**直接对冲** |

#### 点选的区域排序已被试过两次（历史证据）

| 尝试 | 提交 | 结果 |
|---|---|---|
| 区域新度优先（未知连通分量） | `8cc16a4` | **78 分钟后被回滚**（`1edaae8`）：停滞中位 9 s → **56 s（×6.2）**，PASS 5/5 → 2/5，已知面积 −14.9 m² |
| 距离分阶段（先远后近） | `d4eeace` + `8568ca0` | 已实现、默认关、**A/B 跑完但结论从未写入文档** |
| 几何分解区域图 | 本计划 Step 3/4 | 未开始 |

`8cc16a4` 的失败机制（P14 文档 §1 原文）：

> 那次的权重把车推向**远区**，而实测远区目标 **69% 走不到** → 取消 → 进黑名单 →
> 候选池更快耗尽 → 长时间停滞。

**Step 3/4 会原样走进同一个坑**，除非 `door_penalty` + `history_penalty` 真的解决了
"69% 走不到"。这两项目前**一行代码都没有**，也没有任何数据证明它们能治住。

#### 与"先扫框架后补局部"的冲突（必须显式解决）

用户设计的探索策略是**两阶段**：框架阶段（远优先）→ 补齐阶段（就近补）。

- 框架阶段排序：`sorted(items, key=lambda q: (q[1], -q[0]))` → **越远越优先**
- Step 4 区域打分：$\\frac{\\text{unknown\\_gain}}{1+\\text{door\\_penalty}} \\cdot \\frac{1}{1+d(\\text{robot},r)}$ → **越近越优先**

**一个要近、一个要远，同时开启必然对冲。**

⇒ **修订后的 Step 3/4 定位**：区域图**不回答"远还是近"**（那由框架阶段回答），
只回答**"去哪个远区"**。即：

```
框架阶段原本： 所有候选按 -距离 排序 → 最远的赢
改后：        先选"够得着的远区里最有价值的那一个"，再在该区内按 -距离 排序
```

这样距离项不再对冲（都是远优先），而 `door_penalty` 正好用来预判
"这个远区进得去吗"，直接对症 69% 走不到。

### 不做什么

不改车端源码、不引入 vSLAM、不做语义 NN、不换单体栈、不把覆盖率当 KPI、
不做跨会话地图续建（登记为后续，见 §7）。

#### ⚠️ 2026-11-14 实测更正（本节原文有一句是错的，必须改）

本节原文写的是：

> 商用扫地机用的是**几何分解**（扫掠线连通性变化处切开），切出来的胞腔天然有界，
> "房间/区段"就是这么来的。

**这句话是错的。** 2026-11-14 用合成拓扑直接验证了扫掠线分解（Boustrophedon）：

构造 3 个 4×4 m 房间排成一行，相邻之间一道 0.20 m 墙，墙中间开一个可变宽的门：

| 门宽 | 区域数 | 最大区占比 | **检测到的切分点** |
|---|---|---|---|
| **0.00 m**（没门） | **3** ✅ | 33% | — |
| 0.30 m（车过不去） | **3** ✅ | 33% | — |
| **0.45 m** | **1** ❌ | **100%** | **0 次** |
| 0.50 m | 1 ❌ | 100% | 0 次 |
| 0.70 / 0.90 / 1.20 / 2.00 / 3.50 m | **全是 1** ❌ | 100% | 0 次 |

**临界点正好是车宽 0.47 m。** 只要门宽 ≥ 车宽，区域立刻塌成一块，而且
**一次切分都没发生过**。

**原理原因**：扫掠线分解只在"竖切一刀、切出的段数发生变化"时切分。
一堵墙上开个门，那一刀的段数**仍然是 1**（就是门那一段），
所以它**永远不会在门那里切开**。它切的是柱子、走廊岔口这类拓扑，不是门。

> 该算法（Boustrophedon/Morse 分解）在文献里的用途是**覆盖路径规划**，
> 不是房间分割。本计划把两者混为一谈了。

#### 换成什么：按尺度开运算

真能干这份活的是"按尺度开运算"（scale-space opening）：

```
1. 腐蚀（用半径 r 的圆）→ 门缝（宽 2r）被闭合 → 房间彼此断开
2. 连通分量 → 每个分量 = 一个房间
3. 用距离变换把腐蚀掉的空间回填到最近的种子
```

实测（3 房间，门宽 0.80 m，期望恒为 3）：

| 腐蚀半径 | 0.235 | 0.30 | 0.40 | 0.42 | 0.50 | 0.60 | 1.00 | 1.50 | 2.00 |
|---|---|---|---|---|---|---|---|---|---|
| 区域数 | 3 ✅ | 3 ✅ | 3 ✅ | 3 ✅ | 3 ✅ | 3 ✅ | 3 ✅ | 3 ✅ | **0** ❌ |

门宽 × 半径 二维扫描（值 = 区域数，期望 3）：

| 门宽 \ 半径 | 0.30 | 0.40 | 0.50 | 0.60 | 0.80 | 1.00 |
|---|---|---|---|---|---|---|
| 0.50 m | 3 | 3 | 3 | 3 | 3 | 3 |
| 0.70 m | 3 | 3 | 3 | 3 | 3 | 3 |
| 0.80 m | 3 | 3 | 3 | 3 | 3 | 3 |
| 0.90 m | 3 | 3 | 3 | 3 | 3 | 3 |
| **1.20 m** | **1** ❌ | 3 | 3 | 3 | 3 | 3 |
| **2.00 m** | **1** ❌ | **1** ❌ | **1** ❌ | **1** ❌ | 3 | 3 |

**规律是死约束，不是调参能绕的**：

$$\frac{\text{门宽}}{2} < r < \frac{\text{房间半宽}}{2}$$

| 环境 | 门宽 | 房间尺度 | 有效窗口 | 可解性 |
|---|---|---|---|---|
| **家庭** | 0.7–0.9 m | 2–4 m | (0.45, 1.0) | ✅ 一个固定值能吃下 |
| **中小厂房** | 2–4 m | 8–20 m | (2.0, 4.0) | ✅ 也行 |
| **家庭 + 厂房混合** | 0.8 m 门 + 3 m 开口 | — | (1.5,…) 与 (0.4,…) **冲突** | ❌ **无解** |

⇒ **"只有某一种门宽范围内才能分区"这个担心是成立的，而且是原理性的。**
同一建筑里既有 0.8 m 门又有 3 m 大开口（厂房常见：办公区 + 车间）时，
**没有任何单一尺度能同时正确**。

#### 另一处必须更正的背景事实

早先我在汇报里说"本场景是开放式大厅、没有内墙"——**这是错的**。

```
所有批次（p4far / p14vK / p14vL / p14vM / p14vN / p14vP）
使用的 world 全部是 aws_small_house.world
```

该世界是 AWS RoboMaker 小型住宅，含 `RoomWall_01`、4 扇 `FoldingDoor_01/02`、
厨房 / 卧室 / 客厅 / 衣柜 —— **真多房间住宅**。

所以正确的归因是：**不是场景没房间，是扫掠线算法切不开门。**
结论反而更强，因为排除了"场景不匹配"这个借口。

### 1.3 终止判据偏弱

当前探索收敛 = "没有前沿点"。在遮挡/窄道环境下，前沿会先于"可通行空间全部探明"
消失，导致提前收敛。而这不适合"建图供下游导航"的任务——建图是**不可截断目标**
（某区域没建进去，下游导航就会失败），与覆盖任务（允许"这块不扫"）本质不同。

## 2. 设计原则（实施时不得违反）

1. **阈值不得出现在代码里**。任何"米"为单位的判据只能来自 profile 派生量。
2. **能力用 flag 表达，不用机型名分支**。禁止 `if robot == 'ackermann'`，
   只允许 `if not profile.can_rotate_in_place`。
3. **分解用几何，不用连通**。区域边界来自扫掠线连通性变化，不来自 BFS 标签。
4. **默认关闭且逐位等价**。所有新逻辑默认 `false`，关闭时必须与改造前**逐位一致**。
5. **影子模式先行**。新判据先只记录（写 timeline/cand_pool），不参与决策；
   攒够数据再切主路径。
6. **单一事实源**。车体几何只允许在 profile 里定义一次，其他所有地方引用派生值。
7. **可回退**。每个模块一个开关；回退 = 改一个参数，不需要回滚代码。

### M2 扫掠可通行性内核

#### 要修的既有缺陷

`docs/P1_候选生成缺陷清单.md` D2：走廊宽度按**轴向法向**测量，
斜向通道会量出 `真实宽度 ÷ cos45° ≈ 1.41 倍`。根因是 BFS 父格差只能给出
4 连通方向（`(±1,0)` / `(0,±1)`），法向必然轴对齐。

#### 做法

不用"法向测宽"，改用**扫掠**：

```
输入: 路径点序列 P、footprint 多边形 F、占用栅格 G
1. 沿 P 每 res/2 步长取位姿（位置 + 路径切向作为 yaw）
2. 把 F 的每个顶点按位姿变换到世界系
3. 检查多边形内是否有占用格（half-plane 测试 or 预计算模板卷积）
4. 同时输出 swept_min_clearance = 多边形边界到最近占用格的距离
输出: swept_clear = bool, swept_min_clearance, at_index
```

**性能约束**：不能每拍对全图做。约定：

- 只在 `/map` 或 `/global_costmap` 的 `(stamp, w, h)` 变化时重算；
- 只对**当前候选池前 N 名**（`sweep_top_n`，默认 8）做扫掠；
- 单次扫掠预算 `sweep_budget_ms`（默认 30 ms）；超预算就截断并计数
  `sweep_budget_exceeded`，**不允许**静默变慢。

#### 为什么这能带来通用性

| 构型 | 用法差异 | 代码是否需要分支 |
|---|---|---|
| 差速 | 扫掠多边形 = 矩形 | ❌ 不需要 |
| 全向 | 同上，但允许横移→路径切向不必等于车头 | 只需用 `lateral_motion` 决定位姿采样口径 |
| 阿克曼 | 扫掠需沿**转向弧**采样，不用直线 | 由 `min_turning_radius` 决定采样曲线 |

即：**同一份扫掠代码，换 profile 就能服务三种构型。**

### M3 几何分解区域图

#### 与现有实现的关系

- 现有 `unknown_region_field()`（P14/P1）**保留不动**，作为对照；
- 新增 `region_graph` 模块，**默认关闭**；
- 两者互斥：若 `region_graph_enabled=true`，则强制 `ureg_enabled=false`
  （启动时断言，防止两套区域概念打架）。

#### 算法

```
输入: 可导航自由掩码 M（= 已知自由 ∩ footprint 可放置）、地图元数据、尺度 r
1. 腐蚀: E = erode(M, disk(r))
   —— r 必须 > 门宽/2（把门缝闭合）且 < 房间半宽/2（别把房间腐蚀没了）
2. 连通分量: labels = connected_components(E, 8-邻域)
3. 回填: 用 EDT 把 M \ E 的每个格归到最近的种子（保留整块可导航空间）
4. 小胞腔处置: 面积 < min_region_area → 标 unreachable（**不合并**）
5. 建图: 节点 = 胞腔；边 = 共享边界，权重 = 门宽（**只记录，不参与聚类**）；
   附 per-region: area / centroid / unknown_ratio / frontier_count / depth
输出: region_label 栅格 + 邻接图 + per-region 特征
```

> **★ 2026-11-14 两处修订（都有实测依据，见 §1.2）**
>
> 1. **第 2 步：扫掠分解 → 按尺度开运算。**
>    扫掠线分解在门宽 ≥ 车宽（0.47 m）时**0 次切分**，区域恒为 1 块。
>    开运算在门宽 0.50~2.00 m 全部正确。
> 2. **删掉原第 3 步"窄口合并"。**
>    "共享边界净宽 < `pass_width` → 合并"实测让**最大区域膨胀到 99~100%**，
>    比 §1.2 被否掉的连通分量（91.4%）**更退化**。
>    门宽保留在邻接图里供 `door_penalty` 用，**不参与聚类**。

**尺度 r 的取值（唯一必须按场景标定的参数）**：

| 项 | 内容 |
|---|---|
| 硬约束 | `门宽/2 < r < 房间半宽/2` |
| 默认建议 | `r = max(inscribed_radius_m, 0.5 × pass_width_m)`，本车 = **0.45 m** |
| 数据驱动选项 | 从地图统计瓶颈宽度分布，取分位数作 r，**不写死** |
| 混合尺度 | 0.8 m 门 + 3 m 开口 ⇒ **无解**，必须如实报告"不适用"（见 §5-A） |

#### 区域级调度（next-best-region）—— 只在框架阶段生效

用**贪心 GTSP**（不做精确求解）：每拍对未完成区域打分，选最优区域，
再在该区域内选前沿点，交回现有排序链路。

$$\text{score}(r) = \frac{\text{unknown\_gain}(r)}{1 + \text{door\_penalty}(r)}
- \text{history\_penalty}(r)$$

> **★ 2026-11-14 修订：删掉了距离项 $1/(1+d)$。**
>
> 原公式含 $\frac{1}{1+d(\text{robot},r)}$（越近越优先），而框架阶段的排序是
> "越远越优先"（`sorted(items, key=lambda q: (q[1], -q[0]))`，`q[1] = −距离`）。
> 两者**方向相反，同时开启必然对冲**。
>
> 修订后：**距离由框架阶段回答，区域层只回答"去哪个远区"。**
> 补齐阶段（`frame_far_first=false` 或已切到 fill）**不启用区域调度**。

`door_penalty` 来自"进入该区域必须穿过的最小门宽"。

> **★ 补充（2026-11-14）：这个量点级其实也能算。**
>
> 原文断言"这一项是点级排序做不到的"——**不成立**。
> 沿 BFS 路径取 `min(2 × 到最近障碍距离)` 就能得到同一个数。
> 合成验证（两道门，真实门宽 = 0.50/0.62/0.80/0.90/1.20/2.00 m）：
>
> | 真实门宽 | 读出瓶颈 | 误差 |
> |---|---|---|
> | 0.50 | 0.500 | +0.000 |
> | 0.62 | 0.600 | −0.020 |
> | 0.80 | 0.800 | +0.000 |
> | 0.90 | 0.900 | +0.000 |
> | 1.20 | 1.200 | +0.000 |
> | 2.00 | 2.000 | +0.000 |
>
> **零参数、无尺度窗口限制。** 所以实现时优先用"路径瓶颈宽度"，
> 区域图只在需要跨区域整体判断时才用。
>
> 注意：这与 `frontier_arbiter` 里被 2026-11-11（S2）**主动换掉**的
> `2×EDT` 不是同一件事——那个是拿 `2×EDT` 当"走廊宽度"（对前沿点系统性低估，
> 因为前沿点总站在已知/未知交界上），这里是拿它当"**路径瓶颈**"（正是它的强项：
> 瓶颈点两侧都是真实障碍）。

### M4 可导航覆盖率终止判据

#### 定义

$$\text{NCR} = \frac{|\text{已知自由} \cap \text{可导航}|}{|\text{已知自由} \cap \text{可导航}| + |\text{可达未知}|}$$

`可达未知` = 从当前位置出发，允许穿过"未知格"的 BFS 能到的未知格数
（**允许穿未知**是关键：否则窄口外的未知区永远算不到）。

#### 用途分层（2026-11-14 修订）

| 用途 | 行为 | 默认 |
|---|---|---|
| 只记录 | 写 `timeline.jsonl` 与 `ncr` 字段 | ✅ 默认 |
| 收敛告警 | `NCR > ncr_warn_threshold` 时打 WARN + 发布状态 | 可开，`false` 默认 |
| 自动结束会话 | 调 `set_mapping_done` | **阶段 2 有条件开启**（见 Step 5） |

> **★ 2026-11-14 修订说明**
>
> 原文写的是"自动结束**默认禁止**，本计划不实施"，理由是"建图是不可截断目标，
> 拿覆盖率做终止会掩盖缺块"。
>
> 这个担心是对的，但**结论方向反了**：正因为建图不可截断，才不该用
> `no_frontier` 这个**更弱**的判据来终止。当前实现是"没有前沿点就收敛"，
> 遮挡环境下这比覆盖率判据**更容易提前收敛**。
>
> 修订后的做法是**双条件**而非替换：
>
> ```
> 允许收敛 ⟺ no_frontier  AND  NCR > ncr_terminate_threshold
> ```
>
> 即 NCR 只做**否决权**（不准提前收），不做**主动结束权**。
> 这样既不会掩盖缺块，又能治"前沿先于可通行空间消失"的提前收敛。
> 开关 `ncr_terminate`，默认 `false`，阶段 2 验收通过后才开。

### M4b 弓字形覆盖基线（2026-11-14 新增）

#### 为什么要有它

用户原话：

> "弓字形覆盖"是一个极好的强基线：实现简单、代码量小、在你的场景里可能覆盖率
> 不差。**如果它能打平你的 frontier 探索，那正好支撑你的论点——瓶颈不在选点策略。**

这条的价值在于：它是一个**独立的证伪手段**。如果弓字形能打平 frontier 探索，

#### 2026-11-14 离线原型实测（⚠️ 按原文实施会踩同一个坑）

在 5 份真实 `map.pgm`（`p14vP_sw1` / `p14vN_off2` / `p14vM_b2on1` /
`p14vL_s5r1` / `p14vL_s5p2`）上跑了一遍"腐蚀 + 扫掠线分解"，**只做第 1~2 步**：

| 合并阈值 | 区域数 | **最大区域占可导航面积** | ≥1 m² 的区域数 |
|---|---|---|---|
| `gap=0`（不合并） | 55~70 | **21~30%** | 14~17 |
| `gap=0.30 m` | 17~26 | 37~89%（**不稳定**） | 6~8 |
| `gap=0.60 m` | 3~7 | **98~100%** | 1~2 |
| `gap=0.90 m`（= `pass_width_m`） | 3~5 | **99~100%** | 1~2 |

**性能不是卡点**：分解耗时 **4~10 ms**（验收线 100 ms）。

**致命发现**：本节原文第 3 步写的是"相邻胞腔的共享边界净宽 < `pass_width` →
合并"。实测这个取值会让**最大区域膨胀到 99~100%**，比 §1.2 里被否掉的
连通分量方案（91.4%）**更退化**。

根因不是参数没调好，是**场景不匹配**：

| 项 | 值 |
|---|---|
| 场景文件 | `custom_room_2ms.world` |
| 家具 | 6 个 cabinet + bookshelf + 3 根 column |
| **内墙** | **没有** |
| 地图范围 | 11.7 × 19.3 m（234×385 @ 5 cm） |

即这是一个**开放式大厅**，家具之间的通道普遍 > 0.9 m。几何分解在这种拓扑下
本来就切不开——所有空间在"车能过的门"这一判据下是同一块。

**唯一有区分度的定参**：`gap=0` + 面积 ≥ 4 m² 过滤 →

| 轮次 | 腔总数 | ≥4 m² | ≥8 m² | 最大占比 |
|---|---|---|---|---|
| `p14vP_sw1` | 55 | 4 | 4 | 30% |
| `p14vN_off2` | 61 | 4 | 4 | 30% |
| `p14vM_b2on1` | 59 | 6 | 4 | 21% |
| `p14vL_s5r1` | 70 | 4 | 3 | 30% |
| `p14vL_s5p2` | 70 | 4 | 4 | 33% |

→ 区域数 **4~6**，最大占比 **21~33%**。这是当前场景下能拿到的真实上限。

#### 因此对 Step 3 的三条修订

1. **验收指标 ② 换掉**：`区域数 ≤ 40` 是**假指标**——它奖励"少"，而最少就是
   1 个区域，等于没分解。改为 `最大区域占比 ≤ 40%` + `≥4 m² 区域数 ≥ 3`。
2. **合并策略改掉**：不做"`gap < pass_width` 合并"（会退化），改为
   **`gap=0` + 面积过滤**，小胞腔标 `unreachable` 而不是合并。门宽信息保留在
   邻接图里供 Step 4 的 `door_penalty` 用，**不参与聚类**。
3. **本轮不要指望区域级调度的上限很高**：4~6 个区域。Step 4 的 A/B 若要有
   统计意义，需要先接受"区域级只是粗粒度分层"这个定位。

#### Step 3 现在的实际卡点

| # | 卡点 | 严重度 | 能否绕过 |
|---|---|---|---|
| 1 | 验收指标 ② 方向错 | 高 | ✅ 已在本节改为"最大占比" |
| 2 | **场景没有房间结构**，区域级收益上限低 | **高** | ❌ 要么换多房间场景，要么接受 4~6 个粗粒度区域 |
| 3 | 坐标系：`map.pgm` 是 map 帧，仲裁器用 costmap 坐标 | 中 | ✅ 需显式做帧映射（已知有 map↔odom 偏移） |
| 4 | **区域 id 稳定性**：运行时地图持续增长，区域编号每拍变 ⇒ 历史罚分无法累积 ⇒ **Step 4 落不了地** | **高** | ✅ 必须在 Step 3 就解决（映射到固定 id，如按质心最近匹配） |
| 5 | 只有最终快照可测，**没有中间快照**验证运行时行为 | 中 | ⚠️ 需要加"每 10 s 存一份 map 快照"的探针 |

> | s5b2 | 182 | 106 ms | **827 ms** | 1820 ms | 99（54%） |
> | s5b3 | 175 | 68 ms | **512 ms** | 1447 ms | 78（45%） |
> | s5b4 | 188 | 60 ms | **481 ms** | 1951 ms | 84（45%） |
> | s5b5 | 168 | 176 ms | **838 ms** | 1956 ms | 128（76%） |
>
> **轮级 P95 中位 = 512 ms**，即改造**前**就已超过 80 ms 上限 **6.4 倍**。
> 该数值是当初按"tick 成本很低"的估计写下的，不符合实测。
>
> 成本分解（离线复现，单次 `path_and_width` P50 = 30 ms）：
>
> | 段 | 耗时 | 占比 |
> |---|---|---|
> | BFS（budget = max(80000, w·h·2) = 184508 格，Python set） | 29.1 ms | **97%** |
> | `uniform_filter`（未知占比窗口） | 0.66 ms | 2.2% |
> | `reach()` ×2（numpy） | 0.14 ms | 0.5% |
>
> ⇒ 性能预算**只能定成相对基线**，绝对上限必须由 BFS 优化（记为 B2，
> 不在本计划范围）达成后再引入。

| 指标 | 判据 |
|---|---|
| `tick` P95 | **≤ 基线 P95 × 1.5**（基线取 `runs/baseline_frozen.jsonl` 的轮级 P95 中位，2026-11-14 冻结值为 **512 ms**） |
| `tick` 超限拍数占比 | 不得比基线上升超过 10 个百分点（基线中位 54%） |
| `tick` max | 不得 > 基线 max × 1.5（防长尾恶化；基线 max 中位 ≈ 1820 ms） |
| 扫掠单次 | ≤ 30 ms，超预算有计数 `sweep_budget_exceeded` |
| 区域图单次 | ≤ 100 ms，且只在 `(stamp,w,h)` 变化时重算 |
| 内存增量 | ≤ 50 MB |

#### 新增：泛化性判据（2026-11-14）

区域分解的尺度参数 $r$ 有硬约束 $\frac{\text{门宽}}{2} < r < \frac{\text{房间半宽}}{2}$
（见 §1.2 实测）。因此必须显式测"能不能泛化"，而不是只在单一场景上调通：

| 场景 | 门宽 / 房间尺度 | 判据 |
|---|---|---|
| 均质家庭 | 0.7–0.9 m / 2–4 m | 同一 $r$ 必须同时正确切分 ≥ 3 个房间 |
| 均质厂房 | 2–4 m / 8–20 m | 同一 $r$ 必须同时正确切分 ≥ 3 个区段 |
| **混合尺度**（家庭 + 厂房） | 0.8 m 门 **+** 3 m 开口 | **必须如实报告"单一 $r$ 不适用"**，并给出两种 $r$ 各自的失败模式；**不许**用"通过验收"糊过去 |
| 异世界泛化 | `aws_small_house` 以外的 ≥ 2 个世界 | 报告区域数与最大占比，不作通过/不通过判定（探索性） |

> 这一条的存在意义：把"只能某一种门宽范围内才能分区"这个**已知局限**
> 写进验收，而不是留到论文评审时才被问出来。

> **`contact = 0` 的口径（2026-11-13 定稿，不放宽）**
>
> 该判据覆盖**全程，含返航段**，不拆分子段、不设例外。
>
> 历史上它看起来"永远不可能通过"，是因为返航段的盲走式脱困一定会制造接触：
> `p14v6_ab` 中 604 次接触全部来自 sim 242~277 的 9 次
> `forward_escaping_from_stuck_place`（0.05 m/s × 1.8 s/次，净空 0.60 → 0.10 m）。
> **根因已修**（2026-11-13 C/E）：
>
> | 修复 | 位置 | 作用 |
> |---|---|---|
> | 返航段禁用 forward/reverse 盲走 | `manager.start_escape_recovery` | 返航不再产生盲走位移 |
> | 已在容差内→首次脱困即放弃 | 同上（`home_close`） | 原点 1.5 m 内零位移 |
> | 返航重试不再调脱困 | `manager._schedule_return_home_retry` | 重试期间只等 reset 窗口 |
> | 几何到位判据 | `manager._return_home_geometry_satisfied` | 已在容差内且静止 → 直接完成 |
> | 净空环半径上取整 | `manager.current_start_is_map_clear` | `0.40/0.05` 曾算成 7 格 = 0.35 m |
> | unknown 不再当自由格 | `cartographer_manager._fallback_cell_has_clearance` | 返航选点不再落到未知区（`block_unknown=True`） |
>
> 回归测试：`harness/test_return_home_no_contact.py`（13 项断言）。
> 若该测试失败，说明返航零接触的保障已被破坏，**不得**用放宽 `contact` 判据
> 来通过验收。

> **`no_reverse` 的精确含义**
>
> 现有判据是 `checks.no_reverse = true`，对应 `collision.reverse_hard_windows == 0`，
> 即**禁止硬倒车**；软倒车（`reverse_windows` / `reverse_m`）是允许的
> （`p14v6_ab` 实测 `reverse_windows=6`、`reverse_m=1.0`、`no_reverse=true`）。
> 验收目标因此写成：`no_reverse` 判据保持为 `true`，而非"倒车次数为 0"。

## 7.5 计划外追加：返航前不打断导航（2026-11-14 用户要求）

| 项 | 内容 |
|---|---|
| 需求 | "返航前必须要确认是否有导航任务，若有，则等待此轮导航结束、到点后才开始返航，而不是中断正在进行的任务。" |
| 为什么现在做 | 近 4 次失败里 3 次同一个根因：`current pose is too close to occupied /map cells`（`p14vL_s5p2` / `p14vN_off1` / `p14vP_sw2`）。其中 `p14vP_sw2` 是**半路急停**——车以 0.33 m/s 巡航开往 `(6.82,-9.22)`（差 0.99 m）时被 `set_mapping_done` 取消，停在 `(6.244,-10.022)`，随后起点净空校验（0.40 m）不通过 → 3 次重试打满 → 返航失败 |
| 附带发现的死代码 | `session_driver._goal_in_progress()` 读 `nav_goal_active`，而 `manager._publish_state_impl()` 的 payload **从来没有这个字段** ⇒ 恒 False ⇒ 2026-10-26 加的"等候选结束再返航"规则**从未生效**（三轮日志里一次 `=== 等它结束再返航 ===` 都没有） |
| 改动 | `manager.py`：新参数 `return_home_wait_active_goal=True` / `..._sec=45.0`；有活跃目标时进入 `mapping_done_waiting_active_goal` 而不取消；到点后 `mapping_done_active_goal_reached` → 发起返航；目标失败 → `mapping_done_active_goal_failed` → 直接返航（不走探索期脱困）；超时 → `mapping_done_active_goal_timeout` 回退老行为。并补发 `nav_goal_active` / `return_home_requested` |
| | `session_driver`：`_waiting_active_goal` 门禁，防止兜底 cancel-all 把正在执行的目标砍掉 |
| | 实机 launch：显式写入两个新参数（可审计、可回退） |
| 静态验收 | `test_return_home_no_interrupt.py` 21 项断言；已挂进 `smoke_check.sh` |
| **验证方式（2026-11-14 用户指定）** | **不单独立项测试本改动的效果**。返航是**独立于 S5 的 P0**：在 S5 实施测试过程中，**只要出现一次返航失败，立即中断当前批次、深度总结失败原因、查清上下游关系，再汇报** |
| 判据（出现即触发中断） | ① 日志出现 `=== 等它结束再返航 ===` ② 出现 `waiting up to 45.0s` ③ state 序列含 `mapping_done_waiting_active_goal` → `..._reached` ④ **反例**：出现 `..._timeout` ⇒ 45 s 不够，需调大或改判据 ⑤ `return_home=true` 且 `physical_contacts=0` ⑥ 记录回合时长变化 |
| 回退 | `return_home_wait_active_goal=false` |

> **返航 P0 的定位（2026-11-14 用户明确）**
>
> 返航是**独立于 S5 的 P0**，不占 S5 的步骤编号，也不单独开测试批次。
> 它只以"S5 测试过程中的观察项"形式存在：**一旦出现返航失败就中断并深挖**。
> 这样既不额外消耗批次预算，又不会让返航问题被 S5 的进度掩盖。


> **这一步不在原计划里**，但它直接影响 §5-C 的 `contact = 0` 硬性判据
> （覆盖全程含返航段）。它**不插入测试序列**，只作为 S5 各步骤测试时的观察项。
> 归因数据重采（Step 2 收尾）也**不是** Step 4 的前置，两者独立 ——
> 详见 `docs/S5_实施报告.md` 末尾「下一步」一节。
