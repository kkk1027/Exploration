## 0. 一句话结论（先看这个）

**「顶会论文 + Gazebo + Nav2 + RRT」三者同时成立的，本轮检索结果为 0 篇。**

原因不是搜不到，而是结构性的：

- 顶会（ICRA/IROS/RA-L/RSS/CoRL）里的探索论文，**几乎不写 Nav2**。Nav2 是 2021 年后
  才成熟的工程栈，学术工作普遍自带规划器（FUEL 自带 `uav_simulator`，GBPlanner 自带
  `pci_mav`，TARE 自带 `vehicle_simulator`），把它们和 Nav2 放一起反而增加不确定性。
- **写 Nav2 的**（explore_lite 系、`m-explore-ros2`）**算法不是 RRT 系**，
  是最近前沿点 + 代价最小化。
- **写 RRT 的**（`hasauino/rrt_exploration`）是 **ROS1 + move_base**，属于上一代导航栈。

唯一真正把三者凑齐的，是一个**非论文的 ROS2 工程实现**：
`Incomprehensible/RRT_exploration`（ROS2 Humble + `nav2_bringup` + Gazebo Classic + RRT
前沿检测）。它算法源自 Umari & Mukhopadhyay, IROS 2017，但代码本身没有对应论文。

**对我们（P13）最有价值的恰恰是这个：它是唯一一条"和我们技术栈同代"的完整参照实现，
而且作者在 README 里写下的 "Current issues" 与我们要解决的问题几乎逐条对应。**

### T1-1 `Incomprehensible/RRT_exploration`

| 项 | 内容 |
|---|---|
| 标题 | 无对应论文。算法源自 Umari, H. & Mukhopadhyay, S. *Autonomous robotic exploration based on multiple rapidly-exploring randomized trees*, **IROS 2017** |
| 类型 | 开源工程实现（作者自述为 "Mobile Robot Programming experiments"） |
| 作者 | Nadezhda Varzonova（GitHub: `Incomprehensible`） |
| 仓库 | https://github.com/Incomprehensible/RRT_exploration ✅ 已核验 |
| 许可 / 热度 | Apache-2.0，15 ★，2 fork，最近提交 3 个月前 |

**三项条件核验结果**

| 条件 | 判定 | 证据（原文） |
|---|---|---|
| Gazebo | ✅ 是，**Gazebo Classic** | ① README："It was tested on Ubuntu 22.04, with ROS2 Humble and **Gazebo Classic**"；② launch 文件 `SetEnvironmentVariable(name='TURTLEBOT3_MODEL', value='burger')`、`GAZEBO_MODEL_PATH=/opt/ros/humble/share/turtlebot3_gazebo/models`；③ world 默认值 `turtlebot3_gazebo/worlds/turtlebot3_dqn_stage4.world` |
| Nav2 | ✅ 是，**作为导航执行层** | launch 里 `IncludeLaunchDescription(nav2_bringup/launch/tb3_simulation_launch.py, {'slam':'True', 'params_file': <本包>/config/nav2_params.yaml})` |
| RRT | ✅ 是，RRT 前沿检测 | 三个节点：`local_frontier_detector`（局部树，探测到前沿即重置）、`global_frontier_detector`（全局树常驻生长）、`filter`（去旧点/去冗余） |

**仓库内容完整性**

| 组件 | 有/无 | 说明 |
|---|---|---|
| Gazebo world 文件 | ⚠️ **不自带** | 复用 `turtlebot3_gazebo` 的 world（默认 `turtlebot3_dqn_stage4.world`），可通过 `world:=` 参数换 |
| launch 文件 | ✅ 有 | `single_agent_RRT/launch/rrt_exploration.launch.py`，一条命令拉起仿真+Nav2+SLAM+三个RRT节点 |
| Nav2 配置 | ✅ 有 | `single_agent_RRT/config/nav2_params.yaml`，含**自定义 Costmap2D 插件** |
| 可运行说明 | ✅ 有 | `colcon build` → `ros2 launch single_agent_rrt rrt_exploration.launch.py` |
| 依赖说明 | ✅ 有 | PCL（系统装）、nanoflann（已内嵌） |

**可复现性：高**
理由：单条 launch 自包含全部环节；依赖只有 PCL；Humble + Gazebo Classic 与我们环境同代；
无需下载外部数据集或预训练模型。

**该工作指出的痛点（作者 README 原话）**

> "Algorithm finds frontiers very fast in the beginning and as the robot progresses
> but **slows down exponentially when there's not much left to explore**."

> "A special **hash map tracking the already explored areas** shall be added to filter
> out these areas in `filter` node."

> "Currently I added a **custom Costmap2D layer which fixes a bug currently existing in
> Gazebo Classic simulation**. If the bug is fixed for you or you use other versions just
> disable the layer in nav2_params.yaml"

> "Rarely occuring bug in `local_frontier_detector` which I still need to investigate."

> "Current implementation of RRT trees visualization works very slowly in rviz2."

**对 P13 的直接意义**：第 2 条原文就是「RRT 无记忆性 / 重复探索」，而且作者把它列为
**未实现的 TODO**——说明这个痛点在 ROS2 + Nav2 + RRT 这条链路上是**公认未解决**的。
第 3 条则是「探索层与导航栈割裂」在仿真侧的具体表现（探索依赖 costmap，costmap 在
Gazebo Classic 下有 bug，只能靠打补丁绕）。

| 项 | 内容 |
|---|---|
| 标题 | *Autonomous robotic exploration based on multiple rapidly-exploring randomized trees* |
| 会议 / 年份 | **IROS 2017** |
| 作者 | Hassan Umari, Shayok Mukhopadhyay |
| 期刊扩展版 | *Multi-robot Map Exploration Based on Multiple Rapidly-Exploring Randomized Trees*, **SN Computer Science (Springer), 2023**（DOI 10.1007/s42979-023-02193-2） |
| 仓库 | https://github.com/hasauino/rrt_exploration ✅ 620 ★，MIT；教程仓库 https://github.com/hasauino/rrt_exploration_tutorials ✅ 112 ★ |

| 条件 | 判定 | 证据 |
|---|---|---|
| Gazebo | ✅ 是（**Gazebo Classic，经教程仓库**） | 教程仓库自述："provides **all the needed Gazebo simulation files** to bring up Kobuki robots equipped with laser scanners and ready for the rrt_exploration package"；主仓库 README 亦提到 YouTube 播放列表含 "real setup (Kobuki robots) and **simulation (Gazebo)**" |
| Nav2 | ❌ 否，用 **ROS1 `move_base`** | filter 节点订阅 `robot_x/move_base_node/global_costmap/costmap`；assigner 是 `move_base` 的 actionlib client |
| RRT | ✅ 是 | 5 个节点：`global_rrt_frontier_detector`、`local_rrt_frontier_detector`、`frontier_opencv_detector`（非RRT对照）、`filter`、`assigner` |

**仓库内容完整性**：Gazebo world ✅（`single_simulated_house.launch` 等）、launch ✅、
Nav2 配置 ❌（只有 `move_base` 的 costmap 依赖，无 Nav2 参数文件）、说明 ✅。

**可复现性：中**
理由：world + launch + 参数全有，**但整套是 ROS1 Indigo/Kinetic + Python 2.7 + gmapping +
Kobuki 依赖**。要在 Humble 上跑等于重写（filter/assigner 用 Python 2 语法，RRT 检测器是
C++ 但依赖 ROS1 API）。

**该工作指出的痛点**

- filter 节点的去冗余机制只有 `hysteresis_radius`(3.0 m) 与 `hysteresis_gain`(2.0) 两个
  参数，本质是「上一条目标附近的前沿点打折」——**是最原始的记忆机制**。
- README 明确写 filter 的职责包含 "**discards redundant points**"，即冗余前沿被视为
  必治的问题。
- assigner 采用 `revenue = info_gain(radius=1.0 m) × info_multiplier(3.0) − 期望行进距离`，
  **没有任何可通行性/净宽/转角项** —— 与我们 P13 给 `assigner.cpp` 记的账完全一致
  （见 `docs/P13_实施说明.md` §10.4 P13-2B）。

## A. 痛点分析

按「算法层 / 系统集成层 / 仿真到真机层」分类，只列有原文或实验观察支撑的条目。

### A.1 算法层面

**A1-1 RRT 无记忆性 → 重复探索（最硬的痛点，且被公开承认未解决）**

> "A special **hash map tracking the already explored areas** shall be added to filter out
> these areas in `filter` node."
> —— `Incomprehensible/RRT_exploration` README，"Further steps in implementation"

这是我们 P13 里 `rejected_narrow` 累计 547~936 次/轮、同一坐标反复进入候选池的
**同构问题**。作者把它当 TODO，说明 ROS2 + Nav2 + RRT 这条链路上**没有现成答案**。

**A1-2 前沿冗余 → 目标反复重投**

- `hasauino/rrt_exploration` 的 `filter` 节点职责原文含 "**discards redundant points**"，
  去冗余手段只有 `hysteresis_radius=3.0 m` + `hysteresis_gain=2.0`。
- `m-explore-ros2` 最近提交："**Do not blacklist for preempted goal (#51)**" ——
  被抢占的目标要不要进黑名单，至今仍在改。

⇒ 业界做法是「滞后半径 + 黑名单」这种**两参数启发式**，缺乏与我们
`risk_*` 那套 6 项结构化罚分同等级的打分体系。**这是我们可能的差异化空间。**

**A1-3 RRT 后期前沿检测效率指数衰减**

> "finds frontiers very fast in the beginning and as the robot progresses but
> **slows down exponentially when there's not much left to explore**"
> —— `Incomprehensible/RRT_exploration` README，"Current issues"

对应我们实测的 `seen=156~315 点/轮` 但 `risk_eval` 只有 7~45 个——
**候选供给看似充足，实际可用率极低**。

**A1-4 RRT 系行程代价偏高（有对照实验）**

> "**less travel cost than Rapidly Random Tree (RRT)**"
> —— SMMR-Explore (ICRA 2021) README

这是**论文级别的对照结论**，直接旁证我们 P13 三轮 A/B 里
「距离中位始终卡在 4.7~5.4 m、降不到 4.0」不是实现问题，而是 RRT 系的结构性特征。

**A1-5 全局细节处理太慢 → 必须分层**

TARE 的核心动机（RSS 2021 最佳论文）：全局尺度做细节处理不可行，只能
「近处稠密 + 远处稀疏」。与我们 `risk_eval_n=6` 的算力取舍同源。

### A.2 系统集成层面

**A2-1 探索层与导航栈割裂（**这是我们问题的核心，但文献里几乎没有正面处理**）**

- `Incomprehensible/RRT_exploration` 需要**自己写一个 Nav2 Costmap2D 插件**去修
  Gazebo Classic 下的 costmap bug：

  > "Currently I added a **custom Costmap2D layer which fixes a bug currently existing in
  > Gazebo Classic simulation**"

- `hasauino/rrt_exploration` 的 filter 节点**硬依赖** move_base 的 costmap 话题命名
  （`robot_x/move_base_node/global_costmap/costmap`）与「所有 frame/话题必须以
  `/robot_x` 前缀命名」的约定。探索层与导航栈通过**话题名约定**耦合，而非接口契约。

⇒ **我们自己的 `frontier_merge` 是同类割裂的另一种表现**：仲裁器判死胡同的目标，
merge 仍然在 `validated` 超时后原样转发（详见 `docs/P13_实施说明.md` §9.6，
B 组 `raw_deadend=189.8/轮` 而 `raw_publish=1.6/轮`）。

**⚠️ 关键发现：本轮调研的**所有**工作里，没有任何一个存在 `frontier_merge` 这种
「仲裁输出 + 原始兜底」双源结构。** 也就是说，我们遇到的「判决被下游绕过」问题，
在开源社区**没有现成参照答案**。m-explore-ros2 的 blacklist 机制与 hasauino 的
hysteresis 是语义上最接近的两个轻量实现，但都作用在**探索层内部**，不在
「探索层 → 导航层」的边界上。

**A2-2 依赖地狱（决定复现成本的首要因素）**

> "the planner **requires several dependencies**; for example: Mapping framework: either
> Voxblox or Octomap; Planner-Control interface package: pci_mav; MAV simulation: RotorS,
> LiDAR simulator"
> —— `gbplanner_ros` README

对比：单条 launch 自包含的 `Incomprehensible/RRT_exploration` 与 `m-explore-ros2`
复现性都是「高」，而需要「全家桶 workspace」的 GBPlanner 是「低-中」。
**结论：复现成本 ≈ 依赖闭包大小，与算法先进性几乎无关。**

**A2-3 版本漂移（同一份代码在不同发行版上行为不同）**

`m-explore-ros2` README 专门开了一节 TB3 troubleshooting，要求把
`/opt/ros/${ROS_DISTRO}/share/turtlebot3_simulations` 整个替换成上游仓库才能跑。

### A.3 仿真到真机迁移层面

**A3-1 机器人模型不一致**
SMMR-Explore 真机平台是「Jetson Nano + LiDAR 的多车」，仿真用 **TurtleBot3** 模型。
我们自己的链路同样有这个问题：仿真 `wheeltec_two_wheel_model`（footprint 0.50×0.40 m，
对角 0.81 m）与真机参数需要同步维护。

**A3-2 命名空间/frame 强约束**
`hasauino/rrt_exploration` 要求「即使是单机，frame 也必须以 `/robot_1` 前缀命名」。
这类硬编码约定在迁移到已有系统的机器上时要全链路改名。

**A3-3 仿真环境表征方式不同导致结论不可迁移**
FUEL 用 `.pcd` 点云文件而非 Gazebo world 做仿真（RA-L 2021，1521 ★）。
优点是环境易造，缺点是**无法直接验证与物理引擎相关的现象**（碰撞、摩擦、楔死）。
我们 P13 里「脱困能力弱」恰恰是物理现象——**这类结论只能靠 Gazebo 级仿真或真机**。

## B. 可复现可行性判断

### B.1 结论：最低可行路径

**推荐路径：拿 `Incomprehensible/RRT_exploration` 当「参照实现」，不当作「替代品」。**

理由（三条，都可核验）：

1. **技术栈同代**：ROS2 Humble + `nav2_bringup` + Gazebo Classic + SLAM Toolbox，
   与我们（Humble + Nav2 1.1.20 + Gazebo Classic `aws_small_house.world`）一一对应。
2. **单条 launch 自包含**：`ros2 launch single_agent_rrt rrt_exploration.launch.py`
   即拉起「Gazebo + Nav2 + SLAM + 3 个 RRT 节点」。这是本研究里唯一做到这一点的仓库。
3. **它的痛点清单与我们的问题清单几乎逐条对应**（A1-1 / A1-3 / A2-1）。

### B.2 「开箱可跑」程度排序

| 排名 | 仓库 | 开箱程度 | 缺什么 |
|---|---|---|---|
| 1 | `robo-friends/m-explore-ros2` | ★★★★★ | 无（但**不是 RRT**） |
| 2 | `Incomprehensible/RRT_exploration` | ★★★★☆ | 无独立 world（复用 TB3）、无目标分配器（launch 里 `rrt_exploration_node` 被注释，`filter` 之后如何产生 Nav2 goal 需**逐行核验**，我未做） |
| 3 | `acachathuranga/rrt-explore` | ★★★☆☆ | 无 Gazebo world |
| 4 | `caochao39/tare_planner` | ★★★☆☆ | 仿真环境是独立仓库 |
| 5 | `efc-robot/SMMR-Explore` | ★★☆☆☆ | 改版 Cartographer + PyTorch + 需申请下载的模型权重 |
| 6 | `hasauino/rrt_exploration` | ★★☆☆☆ | 整套是 ROS1 |
| 7 | `ntnu-arl/gbplanner_ros` | ★☆☆☆☆ | 需 gbplanner_ws 全家桶 + Voxblox + RotorS |

### B.3 关键组件缺口与工作量

以「在 Gazebo + Nav2 下复现一条 RRT 前沿探索链路」为目标：

| 组件 | 我们现状 | 缺口 | 工作量 |
|---|---|---|---|
| RRT 前沿选择器 | ✅ 已有（`wheeltec_robot_rrt2/rrt_exploration`，`assigner.cpp` 的 `revenue = info_gain×3.0 − euclid_dist`） | 缺净宽 / 逃生方向 / 转角 / 路径宽度项（= 我们的 P13-2B） | **小**（改一个函数，但需在 Jetson 上 colcon） |
| Nav2 行为树配置 | ✅ 已有（`stemm_cartographer_nav_to_pose.xml`，已移除 `GoalUpdater`） | 无缺口 | **无** |
| 探索记忆模块（去重复探索） | ⚠️ 部分有（`_cand_cells` 同格覆盖 + `cand_max_age` 过期） | 缺「已探索区域」的正向记忆（作者 TODO 里那套 hash map） | **中** |
| 探索层→导航层判决传递 | ❌ **无**（`frontier_merge` 无条件兜底 raw） | 需新增「判决发布 + 兜底带判决」协议 | **中**（= 我们提议的 P13-6） |
| Gazebo world | ✅ 已有（`aws_small_house.world`） | 无缺口 | **无** |
| 复现实验脚本 / A/B harness | ✅ 已有（`harness/round.sh` + `p13_ab.sh` + `analyze_dispatch_risk.py`） | **这块我们比上述所有开源仓库都完整** | **无** |

**总判断：我们并不缺「一条 RRT 前沿探索链路」，我们缺的是「探索层与导航层之间的判决传递」。**
复现别人的链路对补这个缺口帮助有限——因为 A2-1 已说明，**没有一个开源项目有这种结构**。

### B.4 因此，外部参考的真实用途是这三件事

1. **借 `m-explore-ros2` 的 blacklist 语义**（PR #51）来设计 P13-6 的「判决表」数据结构：
   被抢占/被判死的目标进黑名单，带 TTL 过期。工作量**小**。
2. **借 `Incomprehensible/RRT_exploration` 的「已探索区域 hash map」TODO** 来做我们的
   探索记忆模块，避免重复造轮子（它连数据结构命名都写好了）。工作量**中**。
3. **借 SMMR-Explore 的「同场景 RRT vs 新方法」双基线 launch 结构**来改进我们的 A/B
   实验设计——特别是它把「RRT 基线」做成了独立节点 + 独立 launch，可以单跑。
   我们目前是**靠环境变量开关同一份代码**（`RISK=0/1`），可复现性略差但改动更省。
