## 2. P13-1 风险评分：为什么是"折现"而不是"罚分"

### 2.1 数据依据

基线（剔除幻影成功后）唯一的统计显著关系是距离：

| 派发距离 | 取消率 |
|---|---|
| <3 m | 19% |
| 3–4 m | 45% |
| 4–6 m | 60% |
| >6 m | **81%** |

转角 / `esc_dirs` / `comp_r2` 各桶**非单调**，有效样本仅 14–55。

### 2.2 公式

```
p(d)  = 1 / (1 + (d / risk_dist_half_m)^2)
score = u_eff * p(d) - aux_落点 - route_沿路
```

`risk_dist_half_m` 默认 **4.5**，三点同时拟合基线：

| d | p(d) | 基线"还能跑完" |
|---|---|---|
| 2 m | 0.84 | ≈0.81 |
| 5 m | 0.45 | 0.40 |
| 9 m | 0.20 | 0.19 |

> 为什么不用"减 35×d"这种小罚分：同样 1000（2 m）vs 3000（9 m）的场景，
> 线性罚分给出 930 vs 2685 —— **远处仍然完胜**，等于没改。
> 折现给出 835 vs 600 —— 远处必须信息量翻倍（6000）才可能胜出。
> `harness/test_risk_scoring.py` 第 3 组断言专门锁住这条性质。

### 2.3 次序项（只降分，永不拒绝候选）

| 参数 | 默认 | 依据 |
|---|---|---|
| `risk_w_turn` | 60 | 转角：基线非单调，只作次序 |
| `risk_w_egress` | 120 | `esc_dirs < 6` 时线性降权 |
| `risk_w_deadend` | 100 | `comp_r2 < 800` 时按比例降权 |
| `risk_w_occ` | 600 | 2 m 窗内 `净空<0.30 m` 占比超过 0.30 后线性降权 |
| `risk_w_route` | 150 | 路径最小净宽低于 **1.20 m** 舒适宽度时线性降权 |
| `risk_occ_soft` | 0.30 | 拥挤阈值 |
| `risk_comp_cells` | 800 | 死口袋阈值 |

> `risk_route_target_m` **不能**取 `pass_width`(0.90)：`path_and_width` 是硬门，
> 能通过的候选必然 `min_w >= 0.90`，取 0.90 会让本项恒为 0（空旋钮）。
> 这是第一版实现里的真实缺陷，被 `test_risk_scoring` 第 4 组断言抓出来。

### 2.4 排序流程的行为变化

改动前：`scored → gate → 逐個硬门检查 → 第一个通过的直接派发`。
改动后：`scored(含折现) → gate(含落点风险) → 硬门 → 收集前 risk_eval_n=6 个合格者
→ 叠加沿路风险后取最优 → 派发`。

**如果只加风险项而不改这一步，风险项对最终结果没有任何影响** —— 因为硬门的
通过顺序与风险无关。这是本次改造里最容易漏掉的一环。

## 3. P13-2A 原始 RRT 候选

### 3.1 问题量化

| 项 | 值 |
|---|---|
| 评分覆盖率 `validated/(validated+raw)` | 22%–60%，中位 ≈37% |
| 能配对到 `candidate_probe.jsonl` 的派发 | 16/297 = **5.4%** |
| 派发来源 | `exploration_rrt` 177 / `exploration_manager` 106 |

车端 `assigner.cpp` 的收益函数只有：

```cpp
info_gain = information_gain(map, frontier, info_radius=1.0);
revenue   = info_gain * 3.0 - 欧氏距离;
```

不含净空、可脱困、转角、路径宽度。而"1 m 内未知格多"恰好与"贴着未测绘边界的
窄处"高度重合。

### 3.2 方案 A 实现

- 新增订阅 `/assigned_frontier_goal`（`robot.cpp` 发的 `PoseStamped`）
- 同坐标 0.30 m 内去重（`assigner` 每 ~8 s 重投同一点）
- 仅在前沿候选与窄缝回退都为空时才接管 —— **不挤占已合格的前沿候选**
- 与前沿候选共用同一风险模型
- 超距保护：`> raw_max_dist_m(8.0)` 只在最近 `raw_starve_sec(6.0)` 没有派发时放行

## 4. P13-4a 脱困目标两轮搜索

### 4.1 问题

| 轮 | `unit_start` | `giveup_40s` |
|---|---|---|
| `v2r1`–`v2r5` | 0 / 0 / 0 / 0 / 0 | 2 / 1 / 1 / 2 / 2 |

同批 148 / 149 / 146 s 的长卡死都伴随"前沿全灭 → 脱困目标"反复返回 `None`。

### 4.2 判据

| | 严格轮（历史行为） | 放宽轮（新） |
|---|---|---|
| 路径窄段 | 一律不派 | 允许，但 `min_w ≥ corridor_hard(0.92)` 且 `unk ≤ corridor_unknown_max(0.35)` |
| 掉头余量 | `≥ return_turn_width(0.85)` | `≥ escape_turn_relax_m(0.70)` |
| 连通区 `comp_r2` | `≥ 500` 硬过滤 | 只参与打分 |
| 搜索半径 | `escape_max_dist(2.00)` | 同 |
| 触发条件 | 总是先跑 | 仅严格轮**全空** |

打分：`2×净空 - 0.6×距离 + 0.5×min(comp,2000)/1000`。

### 4.3 顺带修正

- `escape_need_turn` 改用 `_as_bool()`：原来 `bool(p(...).value)` 会把 launch 传入的
  字符串 `'false'` 当成 `True`（历史踩过同类坑）。
- `escape_max_dist_m` 默认 1.60 → 2.00（仍要求路径可达，只是扩大搜索面）。

## 8. 幻影成功：已修（P13-5）

### 8.1 根因（源码定论，不是推测）

`nav2_behavior_tree/plugins/decorator/goal_updater_node.cpp:53-56`：

```cpp
if (rclcpp::Time(last_goal_received_.header.stamp) >
    rclcpp::Time(goal.header.stamp)) {
  goal = last_goal_received_;          // 实例成员，不随新目标复位
}
```

`last_goal_received_` 是 **GoalUpdater 节点实例的成员**。P12 的 inplace 纠偏
发过一次 `/goal_update` 之后，这个值就永久留在树上；之后每个新的
`NavigateToPose` 目标都可能被替换成那一次旧纠偏点。

于是：`ComputePathToPose` 规划到车当前位置 → path 末位点 ≈ 车位置 →
`ControllerServer::computeControl()` 里 `setPlannerPath()` 设
`end_pose_ = path.poses.back()` 后**第一次** `isGoalReached()` 就命中
（`controller_server.cpp:397`）→ 30 ms "Reached the goal!"。

侧证：`Passing new path to controller.`（`controller_server.cpp:525`，
仅在抢占分支打印）整轮只有 1 次，说明后续目标并未真正换路径。

### 8.2 修复（两处，配套）

1. `wheeltec_ros2/src/stemm_cartographer_exploration/config/stemm_cartographer_nav_to_pose.xml`
   —— **移除 `GoalUpdater` 装饰器**，恢复 `Fallback` 直接包 `ComputePathToPose`，
   并在文件内写明根因与恢复方式。
2. `frontier_arbiter` 的 `veto_inplace` —— 即使被设为 `true` 也**强制降级**为
   `veto_migrate`，并打 error 日志。否则 `/goal_update` 发出去无人消费，
   等于静默失效。

> 仿真侧是软链安装（`install → build → wheeltec_ros2/src`），
> 所以**改源码即生效，不需要 colcon**。已验证：
> `readlink -f install/.../config/stemm_safe_nav2_params.yaml`
> → `wheeltec_ros2/src/.../stemm_safe_nav2_params.yaml`。

### 8.3 为什么不改 `goal_checker.stateful`

`stateful: True` 只是**放大器**（锁存后车离开也仍报到达）。真正让 30 ms 就命中
的是 `end_pose_` 落在车身上，与 `stateful` 无关。
按最小改动原则**没动它**（两份参数的 `stateful` 保持原值）。
若日后 A/B 里 `phantom_rate` 仍不为 0，再考虑。

### 8.4 恢复 inplace 的前提

必须先解决"GoalUpdater 跨目标污染"，可选路径：
- 升级 nav2 到提供重置接口的版本；
- 自定义一个 BT 节点，在 goal 变化时清空 `last_goal_received_`；
- 不再用 `GoalUpdater`，改回 `veto_migrate`（cancel + 立即重派）。

### 8.2 P13-3 硬门降级（已获批准，但本轮未做）

`pass_width_m(0.90)` / `narrow_len_max_m(1.00)` / `unknown_span_max_m(0.35)`
三处硬门会掐供给（单轮 `rejected_narrow 256`、`rejected_path 122`）。
按批准意见应降级为软约束，但**必须等 P13-1 的 A/B 出结论后再动**，
否则无法区分"评分变好"与"供给变多"的贡献。

### 8.3 P13-4b 看门狗取消策略（已获批准，但本轮未做）

`explore_watchdog` 5 s → `cancel-all` 与 `escape_supervisor` 的 `nav_busy`
前置条件互斥（前者取消后后者永远起不了单元）。计划改为"先请求脱困，
8~10 s 仍无位移再取消"。同样排在 A/B 之后。

### 8.4 既有失败（与本次无关）

`harness/test_param_types.py` 有 12 项 FAIL，全部是 `round.sh` 早期
`{VAR:-default}` 未展开的写法（`MERGE_TTL`、`NEAR_FIRST_R` 等）。
用 HEAD 版本复跑结果完全一致，确认是既有问题，本次未触碰。

### 9.2 第一轮失败根因 —— P13-2A 绕过了硬门（已修 `dc293fd`）

从 `p13ab_b*` 的 360 条探针记录里逐条对比两个来源：

| 来源 | esc_dirs | min_w | dist |
|---|---|---|---|
| `frontier` | 8 | 1.30 | 4.00 |
| `raw_rrt` | **0** | **0.00** | 5.50 |

`raw_rrt` 分支 258 次尝试，**全部**是"零逃生方向 + 零路径宽度 + 远距离"。
代码层面原因在 `pick_raw_goal()`：

```python
ok, _narrow, min_w, unk = self.path_and_width(...)   # narrow 被丢弃
```

`narrow`（走廊/窄道标记）被 `_` 丢掉，于是窄道判据对 raw 分支完全不生效；
而 `risk_w_egress=120` 是**加性**惩罚，压不过 `u*p ≈ 1000` 的量级。

修法（`dc293fd`）：raw 分支必须走同一套硬门 ——
`raw_require_narrow_free=true`（`narrow is not None` 直接跳过）
与 `raw_min_esc_dirs=3`。修复后 `raw_publish` 从 258 降到 0~4。

| `raw_narrow` | 31.0 |
| `raw_unreachable` | 21.8 |

即：**RRT 的原始目标 98.6% 被仲裁器判定为死胡同/窄缝/不可达**，
判断本身是对的（`raw_deadend` 189.8/轮），但 `frontier_merge`
在 `validated` 超过 5 s 未更新时**照原样把这些目标转发给 manager**：

```python
def on_raw(self, m):
    if self._last_validated is not None and (now - self._last_validated) < self.ttl:
        self.stats['merge_suppressed'] += 1
        return          # 只在"仲裁器刚通过过"时压掉
    ...                 # 否则无条件转发，不看仲裁器对这条目标的判决
```

这就是"**经常被派发难以脱困的候选**"的机制性来源：
候选被识别出来了、被否决了，然后被下游绕过否决再送进 nav2。

> `frontier_merge` 之所以存在，是因为历史单源化实测会让 manager
> 空等 92 s（见该文件头注释）。所以**不能**简单删掉 raw 兜底，
> 只能让兜底"带判决"：仲裁器明确判死的目标，兜底也不许转发。

## 11. P13-6 判决传递（typed frontier output）

### 11.1 动机（来自 §9.6 的实测）

`p13d` B 组 5 轮均值已经把瓶颈钉死在「判决传递」而不是「判决质量」：

| 统计 | 值 | 说明 |
|---|---|---|
| `raw_seen` | 165.6 /轮 | 仲裁器看到的 RRT 原始目标 |
| `raw_deadend` | 189.8 /轮 | 其中被判「无逃生方向」 |
| `raw_publish` | **1.6 /轮** | 判决后真正放行 |
| merge `raw` | 35~93 /轮 | **下游仍转发** |
| 派发带评分特征占比 | **16%** | 84% 无评分数据 |

判决本身是对的（98.6% 该拒），但它**从未离开仲裁器**。

### 11.2 接口契约

判决消息用 `std_msgs/String` 承载 JSON（避免新增 msg 包需要重编）：

```json
{"k": [qx, qy], "x": 1.05, "y": -0.45, "v": "dead_end", "s": 2.0}
```

- `k`：0.30 m 网格量化键，**由发送方给出**，接收方不重新量化（避免两侧漂移）
- `x`/`y`：原始坐标，供接收方按半径匹配
- `v`：`feasible` / `dead_end` / `too_narrow` / `unreachable` / `over_dist`
- `s`：分数（负判决时为 `esc_dirs` / `min_w` / 距离，供归因）
- **刻意不带时间戳**：发送方用 `time.monotonic()`，接收方用 `/clock`（仿真时间），
  混用在 pause/reset 后会产生负年龄，导致 TTL 判定永远成立或永远失效。
  由接收方按**到达时刻**计时。

### 11.3 关键实现细节（都是踩过坑才写对的）

1. **判决必须打在原始坐标 `(rx, ry)` 上，不能打在回拉后的 `(gx, gy)` 上。**
   `merge` 看到的是 assigner 投递的原始点，用回拉点做键永远匹配不上。
   这一条已由 `test_verdict_propagation` §8 断言锁住。

2. **只在判决翻转时发布**，其余靠 `verdict_period`（2 s）全表快照重发。
   快照让「merge 后启动」和「丢包」都能自愈，同时不刷屏。

3. **饿死保护 `force_after_sec`（默认 15 s）**：
   若连续这么久没有任何目标输出给 manager，就无视负判决放行一条。
   没有它，上游把 raw 全判死（实测 dead_end 占 98.6%）会导致 manager 永远等不到
   目标 —— 这正是历史单源化造成 92 s 空等的成因（`frontier_merge` 文件头注释）。

4. **判决拦截放在限速/去重之后。**
   限速与去重是廉价的一次性筛，判决查询要遍历表；放在之后可让每条被拦下的
   消息都是「本来真的会发出去」的那一条，使 `merge_verdict_block` 与
   `merge_raw` 在同一口径上可比。

5. **被拦下的目标不更新 `_last_raw`**，否则下一条会被 `raw_period`(0.5 s) 白等。

6. **`verdict_enabled` 依赖 `raw_score_enabled`。**
   判决只在 `pick_raw_goal()` 里产生，该函数在 `raw_score_enabled=False` 时
   直接返回。两者不一致时判决通道会**静默失效**，因此 `__init__` 里加了显式告警。

### 11.4 新增指标：VBR（判决绕过率）

$$\text{VBR} = \frac{N_{\text{blocked}}}{N_{\text{blocked}} + N_{\text{forwarded}}}$$

- `VBR = 0` ⇒ 通道形同不存在
- `VBR = 1` ⇒ 全靠拦截，下游会饿死（须同时看 `force_pass`）

由 `harness/analyze_dispatch_risk.py` 的 `_verdict_report()` 计算，
**只在确实跑了判决通道的轮次上输出**，老轮次不会出现 `VBR=0%` 的误读。

### 11.5 参数

| 侧 | 参数 | 默认 | 说明 |
|---|---|---|---|
| arbiter | `verdict_enabled` | `true` | 是否发布判决 |
| arbiter | `verdict_topic` | `/frontier_verdict` | 判决话题 |
| arbiter | `verdict_period_sec` | `2.0` | 快照重发周期 |
| arbiter | `verdict_ttl_sec` | `6.0` | 快照里保留多久 |
| merge | `verdict_enabled` | `true` | 是否按判决拦截 |
| merge | `verdict_ttl` | `6.0` | 判决有效期 |
| merge | `verdict_radius` | `0.45` | 坐标匹配半径（m） |
| merge | `force_after_sec` | `15.0` | 饿死保护阈值 |

`harness/round.sh` 透传 `VERDICT` / `VERDICT_TTL` / `VERDICT_R` / `VERDICT_FORCE`；
`harness/p13_ab.sh` 里 A 组 `VERDICT=0`、B 组 `VERDICT=1`。

### 11.6 离线验证

`harness/test_verdict_propagation.py` —— 8 组、46 项断言，全 PASS：

1. 跨模块契约：两侧负判决集合必须完全一致
2. `parse_verdict` 对坏消息容错（坏 JSON / 缺字段 / 非数字）
3. `lookup_verdict` 的半径 / 时效 / 取最新（判决可翻转）
4. `_verdict_gate` 四条分支 + 四类负判决逐一验证
5. 饿死保护（含「恰好等于阈值应放行」的边界，防浮点抖动永久拦截）
6. 量化网格一致 + 只在翻转时发布
7. 快照重发与过期不重发
8. 各层默认值一致 + 判决打点位置正确

其中 §5 的「40 条全负判决里最终必须有放行」是端到端不变量：
它保证饿死保护不是装饰品。

### 12.3 这个结果的含义（对论文最关键的一段）

这是**负面结果**，但比正面结果更有信息量：

1. **VBR 63% 证明"判决从未离开生成器"这个诊断是对的**。
   在 A 组（`VERDICT=0`）VBR 恒为 0 —— 通道不存在时，下游 100% 无条件兜底。
2. **单纯"拦截"不是解法**。判决拦截掉了坏目标，同时也拦掉了**唯一的兜底供给**。
   这与历史教训（单源化导致 manager 空等 92 s）同源：
   raw 兜底之所以存在，是因为仲裁器供不起货（每轮仅 32 条）。
3. **饿死保护形同虚设**：10 轮只触发 1 次。`force_after_sec=15 s` 太宽松 ——
   判决有效期内（`verdict_ttl=6 s`）总有新 raw 到达，`_last_out` 不会真的空等 15 s。
   ⇒ E2 必须把 `force_after_sec` 压到 5~8 s 量级重测。

### 12.4 已定位并修复的设计缺陷：契约退化成纯黑名单

**现象**：`merge_verdict_ok = 0`（10/10 轮），B 组没有任何 `feasible` 判决被消费。

**实测数据（p13e1_b3 末次累计）**：

| 判决类型 | 条数 |
|---|---|
| `dead_end` | 186 |
| `too_narrow` | 50 |
| `unreachable` / `over_dist` | 0 / 0 |
| **`feasible`** | **3** |
| 合计 `verdict_pub` | 321 |

**根因（源码级）**：`pick_raw_goal` 的候选循环是
```python
for ... in scored[:self.raw_score_n]:      # 只看 top-3
    ...
    if best is None or (sc - route) > best[0]:
        best = (...)                        # 只有胜者留下
...
self._record_verdict(rx, ry, 'feasible', ...)   # 循环外，只给胜者发
```
两个问题叠加：

1. **只评估 top-`raw_score_n`（默认 3）**。每拍只要这 3 个都落在死角，
   整拍就没有任何 `feasible` 产出，而 merge 侧可能持有 20+ 条 raw 待判。
2. **`feasible` 只发给"本拍胜者"**。语义错了 ——
   判决应当描述**该候选自身可不可信**，而不是"它是不是这一拍的赢家"。
   结果判决表里清一色否决，merge 没有可回退的批准池，
   只能对所有 raw 一律拦截 → 供给塌陷。

**修法**：
- 评估范围放开到全部 `scored`（硬门已由 `esc/可达/窄缝` 三个分支把关，
  放开范围不会放过坏目标）；
- 每个通过全部硬门且不超距的候选**各自**发 `feasible`（带自己的 `risk_total`）；
- 超距候选保留为 `over_best` 而不是 `continue` 掉（否则超距保护与饿死绕过
  都会变成死代码），仅在饿死时才允许派发并补发 `feasible`。

已由 `test_verdict_propagation` 的 §9（5 项断言）锁住。

### 12.5 仍需处理的问题

1. **`force_after_sec=15 s` 形同虚设**：10 轮只触发 1 次。
   因为 `verdict_ttl=6 s` 内总有新 raw 到达，`_last_out` 不会真的空等 15 s。
   ⇒ E2 必须把它压到 5~8 s 量级重测。
2. **`verdict_recv` 远大于 `merge_raw + block`**（如 b2：454 接收 vs 34+58=92）：
   2 s 全表快照重发带来大量重复，统计口径需改为去重后上报。
2. **`verdict_recv` 远大于 `merge_raw + block`**（如 b2：454 接收 vs 34+58=92）：
   快照重发（2 s 全表）导致大量重复，统计口径需要按"首次"或去重后上报。
3. **单环境**：全部 20 轮都在 `aws_small_house.world`，泛化性未知（E3）。

### 12.6 与历史基线的对比（说明实验质量）

E1 的 A 组（10 轮）取消率 76.4%、距离中位 4.61 m、已知格 61432。
历史 `p13d` B 组（5 轮）取消率 73.5%、距离 5.01 m、已知格 61930。
两者同量级，说明 E1 的 A 组基线是可信的，没有引入新的系统性偏差。

### 12.7 更根本的发现：判决判据在 RRT 候选上无区分度

上节的"只发胜者"修正**并没有真正解决问题**。在 `p13e2_inf1`（含修正）里仍然：

| 统计（sim=411 末次） | 值 |
|---|---|
| `raw_seen` | 158 |
| `raw_deadend`（累计判断次数） | **158** |
| `raw_narrow` | 56 |
| `raw_unreachable` | 4 |
| `verdict_feasible` | **0** |
| `raw_publish` | **0** |
| merge `block` / `raw` | 73 / 12 |

`merge_raw=12` 且 `merge_verdict_none=12` —— 那 12 条**全是"没有判决"而按历史行为
转发的**。凡是有判决的 raw（73 条）**全部被拦**。

⇒ **`raw_min_esc_dirs=3` 这个判据在 RRT 生成的 raw 候选上几乎无法通过**，
`feasible` 恒为 0，契约在功能上退化成"纯黑名单 + 节流器"。

这不是实现 bug，是**判据与目标分布不匹配**。RRT 的前沿点被 `pull_back`
拉到已知自由空间边缘，那里的「可脱困方向数」普遍 < 3。

### 12.8 这对论文意味着什么（需要重新定位）

原假设是「判决对了但传不出去」。实测把假设推进了一层：

**判决传出去了，但判据本身在目标分布上没有区分度** ——
它把 100% 的 raw 判死，于是：
- 要么全拦（供给塌陷，E1 的 B 组就是这情况）
- 要么靠 `force_after_sec` 定期放行（退化成采样节流）

两条路都不是"用判决提升质量"。所以论文的立论必须调整，见下一节。

### 12.9 三条可能的论文路线（按证据强度排序）

| 路线 | 主张 | 现有证据 | 需补的工作 |
|---|---|---|---|
| **R1 诚实负面结果** | RRT 前沿的 raw 兜底供给质量极差（100% 无可脱困性），"跨层传判决"这一层抽象无法带来收益，因为判据本身无区分度 | ✅ 已很硬（E1 的 5/9 显著 + 本条 100% 判死） | E2 作为"节流曲线"呈现即可 |
| **R2 供给侧的账** | 真正该修的是**仲裁器供给量**（validated 仅 21~32 条/轮，而 raw 51 条/轮但全是垃圾）；判决传递暴露了这个结构性失衡 | ✅ E1 因果链已量化 | 需要做"提升 validated 供给"的实验（改 arbiter 而非传判决） |
| **R3 判据标定** | `esc_dirs` 阈值需要按目标分布标定，而非拍脑袋取 3 | ⚠️ 只有"100% 判死"这一个点 | 需要扫描 `raw_min_esc_dirs ∈ {0,1,2,3}`，看 feasible 率与质量的关系 |

**建议**：R1 + R2 组合。R1 是已经坐实的事实，R2 是它的直接推论。
R3 作为补充实验（工作量小，`p13_sweep.sh` 一条命令即可）。

**设置**：`harness/p13_sweep.sh p13e2 5 180.0`，4 臂交错执行。

### 13.1 无效轮剔除（方法学，必须先说）

`p13e2_f82`（f8 第 2 轮）因 sensor preflight 超时，`published=0`、

更隐蔽的是它的 `timeline.jsonl` 有 123 行（启动心跳），

### 13.2 主结果：`force_after_sec` 在 5~∞ 范围内**对质量无显著影响**

各臂与 `inf` 基线的配对 bootstrap（1000 次，按轮号配对）：

（`force` 越小放行越多，拦截占比越低），它反映的是"阀门开多大"，

### 13.4 为什么检不出差异：统计功效不足（如实说明）

各臂 `cancel_rate` 的组内波动：

**只能检出极大的效应**。所以「无显著差异」应读作
**「在本样本量下检不出」**，而不是「确定无效」。

要真正判定，每臂需 ≥15~20 轮（按 CV 15%、目标检出 15 pt 估算）。
本轮 20 轮 × 4 臂已耗约 3 h，扩到 4×20 需约 12 h。

### 13.5 E2 + E5 合起来说什么（对论文最关键）

1. **饿死保护这个对偶约束，在实测中没有起作用**。
   10 轮 E1 里只触发 1 次，E2 各臂里 `f15`/`inf` 触发 0 次。

2. **`force` 参数只在"大量拦截"时才变成主控旋钮**（`f5` 触发 13 次/5 轮），

3. 合并 §12.7 的发现（`raw_min_esc_dirs=3` 判死 100% raw），
   整条链路的真相是：

   > **判决通道 100% 输出否决 → merge 只能拦截 → 拦截削减供给 →
   > 饿死保护本该补回供给，但它要么不触发、要么放行的也是垃圾。**

   所以「判决传递」这层抽象在当前判据下**无法产生净收益**。

## 14. E6 实测结果（`raw_min_esc_dirs` 标定，4 臂 × 5 轮）—— F1 坐实

**设置**：`harness/p13_sweep.sh p13e6 5 180.0`，4 臂交错，每臂 5 轮共 20 轮。
共同基线 `VERDICT=1 RAW_SCORE=1 ESC_ALLOW_NARROW=1 ROUTE_GATE_SOFT=1`，
唯一变量 `RAW_MIN_ESC ∈ {0,1,2,3}`（0 = 把这条判据完全关掉）。

### 14.1 主结果：四个臂的 `feasible` **全部为 0**

| 臂 | `RAW_MIN_ESC` | 轮 | `feasible` | 负判决和 | **feasible%** |

| `e2` | 2 | 5 | **0** | 288 | **0.0%** |
| `e3` | 3（默认） | 5 | **0** | 272 | **0.0%** |

**把 `raw_min_esc_dirs` 从 3 一路调到 0（完全关闭这条判据），`feasible` 仍然是 0。**

### 14.2 为什么：拒绝在硬门之间**守恒转移**

| 判决类型 | `e0`(esc=0) | `e3`(esc=3) | 变化 |
|---|---|---|---|
| `dead_end` | 0 | 248 | **+248** |
| `too_narrow` | **161** | 17 | **−144** |
| `unreachable` | **69** | 7 | **−62** |

| **负判决和** | **230** | **272** | +42（≈守恒） |

关掉 `esc` 门之后，`dead_end` 归零，但 `too_narrow` 与 `unreachable`
立刻顶上（161 和 69）。负判决总量 230 → 272，几乎不变。

⇒ **「判据无区分度」不是某个阈值太严，而是所有硬门联合后，
对 RRT raw 候选的拒绝率恒为 100%。** 这是"守恒的拒绝"（conserved rejection）。

### 14.3 交叉验证：四臂的质量指标也全部无显著差异

| VBR | 72.1% | 66.7% | +3.7 | [−17.0, +10.4] | 无显著 |
| 已知格数 | 59070 | 60813 | +417 | [−2059, +3434] | 无显著 |

**9 项指标全部无显著差异。** 这与 §14.1 完全自洽：
既然四臂的判决都只有"拒绝"（`feasible=0`），
那它们在功能上就是**同一个纯黑名单**，指标当然一样。

四臂的供给量也印证这点：

| 臂 | supply | validated | raw | VBR |
|---|---|---|---|---|

### 14.4 这解释了 E1 与 E2 的全部结果

三个实验现在串成一条完整因果链：

1. **E6**：判据对 RRT raw 的拒绝率恒为 100%（无论阈值怎么调）
   ⇒ 判决通道只能输出否决。
2. **E2**：既然只有否决，"饿死保护"就成了唯一放行通道；
   但它在 5~∞ 范围内对质量无显著影响 —— 因为它放行的也是垃圾。
3. **E1**：判决通道开着（`VERDICT=1`）相对关着（`VERDICT=0`）的唯一效果
   就是把 raw 兜底供给从 51 砍到 22（−57%），
   换来的是覆盖面显著下降（−5237 格），而 4 项质量指标全无显著改善。

### 14.5 结论（论文的核心命题）

> **在 RRT 前沿探索 + Nav2 这条链路上，"把探索层的可行性判决传给导航层"
> 这一架构改进无法产生净收益，因为判决判据对 RRT raw 候选的拒绝率恒为 100%
> —— 无论怎样放宽单一阈值，拒绝都会守恒地转移到其他硬门。
> 判决通道因此必然退化为纯黑名单，而纯黑名单只能削减供给，不能筛选质量。**

要提升派发质量，必须改**供给生成端**（RRT 前沿点本身的质量），
而不是在探索层与导航层之间加一层判决。

### 14.6 方法学备注（这次踩到的坑）

`p13_sweep.sh` 收尾汇总把 glob 写在了双引号里
（`ls -d "logs/round_*_${PREFIX}_${label}${i}"`）——
bash 在引号内不展开通配符，于是 20 轮全部有 450+ 行数据却报"0/5 轮可用"。
已改为 `for cand in logs/round_*_...; do` 形式。
这类"假阴性"很危险：它会让人误以为数据没采到而重跑，白烧 3 小时机时。

## 15. S1~S4：从"堵塞供给"转向"修正测量"（2026-11-11）

### 15.1 起因：日志里两条被误读的现象

用户提出两个疑问：① 小车前往候选途中为何"无故终止"候选；② 为何长时间原地滞留。
对 63 轮 `p13e1/p13e2/p13e6` 日志做静态统计后，结论是**两个问题是同一个根**：
仲裁器内部有两套互不相让的"合格判定"。

**滞留（37% 的探索时间）**

| 指标 | 值 |
|---|---|
| 前方净空 >1.2 m 却静止的采样 | 4154 / 11231 s = **37%** |
| 这类 ≥5 s 滞留片段 | 292 段，4.6 段/轮，中位 8 s，最长 85 s |
| 滞留期间状态 | `waiting_for_rrt_frontier` 占 **84%**（245/292） |

→ 不是被挡，是**没目标可去**。

在 2493 s 的"等目标"时间里，各计数器增量（`timeline.jsonl` 逐秒差分）：

| 计数 | 增量 | 折合 |
|---|---|---|
| `reject_narrow_hard` | +73477 | **29.5 次/秒** |
| `published` | +233 | 0.09 次/秒（11 s 才 1 个） |

**中途终止（6.5 次/轮）**

| 指标 | 值 |
|---|---|
| 取消紧跟在 `V2-③ 后置迁移` 之后 1.5 s 内 | **55%** |
| "派发→撤销"存活时长 | 10% 分位 **0.2 s**、中位 5.5 s |
| 存活 <3 s | **40%** |

### 15.2 根因一：宽度测量对前沿点系统性低估（S2）

旧实现 `frontier_arbiter:path_and_width`：

```python
d, unk_ = self.clearance_at(field, wxp_, wyp_)
width_ = 2.0 * d        # 假设两侧对称
```

`d` 来自"到最近已知占据格的距离"（未知格不算障碍）。而**前沿点永远站在
已知/未知交界上**，典型几何是

```
[已知墙] ←0.45 m→ [候选] ←开阔未知 4 m，无占据格→
```

此时 `d = 0.45` ⇒ `width_ = 0.90` < `corridor_hard 0.92` ⇒ 判死，而物理上右侧有 4 m。

**关键性质：`2d` 是总宽的*下界***（最近障碍必然只出现在某一侧）。
所以改为"沿法向两侧实测求和"后，宽度**只会变大或相等，不会变小** ——
不引入新的不安全，只去掉低估。

实现：新增 `_path_lateral_widths()`，用 numpy 批量沿法向两侧采样距离场，
取"第一次撞到障碍前的步数 × res"作为该侧距离，两侧相加，最后与 `2d` 取 `max`
作为保险。性能实测：2400 点路径 **1.9 ms/次**（可忽略）。

|---|---|---|---|
| A 对称走廊（间距 2.0 m） | 2.00 | 2.00 | 相等 ✅ 不放大 |
| B 单侧墙 0.45 m + 另一侧开阔 | 0.90（被误杀） | 1.30 | 越过门槛 ✅ |
| C 随机障碍，逐点断言 | — | 新 ≥ 旧 | 最小差值 = 0.0000 ✅ |

### 15.3 根因二：硬门把"能过但窄"也判死（S3）

旧逻辑只有一道 `corridor_hard = 0.92` 硬门。真实几何下界是
"车宽 0.40 + 两侧各 0.09" = **0.58 m**。所以拆成两档：

| 净宽 | 处理 |
|---|---|
| `< narrow_floor (0.58)` | 硬拒（物理过不去，保留防楔死能力） |
| `[0.58, 0.92)` | **放行 + 罚分 1.0→2.0**（越窄罚越重，但不否决） |
| `[0.92, 1.20)` | 放行 + 罚分 0→1.0 |
| `>= 1.20` | 不罚 |

罚分单调连续（在 0.92 处两段都 =1.0），乘以 `risk_w_route=150` 进入排序。
新增计数器 `pass_narrow_soft` 观测"救回多少供给"。

### 15.4 根因三：后置否决只剩"取消"这一条路（S4）

`P12` 曾实装 `inplace`（原地改向，不取消目标），2026-11-09 因
**79.2% 的 30 ms 假到达**被强制停用，并从 BT 删掉 `GoalUpdater`。

根因是 nav2 上游缺陷（`nav2_behavior_tree/plugins/decorator/goal_updater_node.cpp`）：

```cpp
if (rclcpp::Time(last_goal_received_.header.stamp) > rclcpp::Time(goal.header.stamp)) {
  goal = last_goal_received_;      // last_goal_received_ 永不清理
}
```

`last_goal_received_` 是实例成员且从不复位，判断完全押在时间戳比较上。
BT 里 `input_goal.header.stamp` 常为 0 ⇒ `T > 0` 恒真 ⇒ **每个新目标都被替换成
历史上那一次的纠偏点** ⇒ 车已在该点 ⇒ controller 首次 `isGoalReached()` 命中。

修复（3 处）：

1. `goal_updater_node.hpp`：新增 `goal_cache_valid_ / prev_goal_x_ / prev_goal_y_`
2. `goal_updater_node.cpp::tick()`：`input_goal` 位置变化 > 5 cm 即判定"换了新目标"，
   丢弃 `last_goal_received_`。跨目标污染因此不可能发生，同一目标内仍正常接受纠偏。
3. `frontier_arbiter::_publish_goal_update()`：发布前检查
   `/goal_update` **订阅者数量**，为 0 时返回 `False` 并退回 `migrate`（取消重派）。
   这样"开了 `veto_inplace` 但 BT 没挂 GoalUpdater"不会静默失效。
   `veto_inplace` 的强制降级改为警告 + 允许配置（默认仍 `False`）。

同时准备好可选的 BT 文件（实际生效版在 `wheeltec_ros2` 仓库，见 §15.11）：
`src/stemm_cartographer_exploration/config/stemm_cartographer_nav_to_pose_goalupdater.xml`
（与车端原树逐节点相同，唯一差异：`ComputePathIfNeeded` 外包一层 `GoalUpdater`），
**默认不启用**。

### 15.12 inplace 的「记账口径偏差」—— 必须知道的副作用

S4 启用 inplace 后，manager 的 `reached; ... error=(xy=X m)` 会**天然偏大**，
原因不是车开错地方，而是**记账口径不一致**：

```
仲裁器:  /goal_update 把目标 G → G*（附近合格点，可能 3 m 外）
controller: 到 G* 即判 succeeded（它只收到过 G*）
manager:  仍按原目标 G 记账 → 误差 = |车 - G| 而不是 |车 - G*|
```

**实测铁证（p13s4_g4 第 1095 行）**：

| 事件 | 时间 | 坐标 |
|---|---|---|
| 派发目标 G | 4642.00 | (9.20, 0.58)，车在 (8.00, −7.75) |
| inplace 纠偏 G→G* | 4660.60 | (9.20,0.58) → **(6.45, 1.62)**，距离 2.95 m |
| 到达 | 4679.46 | 车在 **(6.55, 1.69)** |

- 车到 **G\*** 的距离 = 0.122 m（正常收敛）
- manager 记录的误差 = **2.875 m**（按 G 算的）
- 存活时长 = **37.5 s**（不是幻觉的 30 ms）

**所以「到达误差」这一指标在 S4 前后不可直接比较。**
为此新增 `harness/s4_ghost_audit.py` 自动区分：

| 判定 | 条件 |
|---|---|
| 正常（inplace 记账） | 到达前有该目标的 inplace 记录，且 \|车 − G*\| < 0.5 m |
| 正常（普通收敛） | 存活时长 > 5 s |
| **疑似幻觉** | 存活 ≈ 30 ms 且车几乎没动（P13-5 的老症状） |

**实测结果（g1~g5，28 条到达）**：

```
轮次    正常到达  疑似幻觉
g1          3        0
g2          6        0
g3          4        0
g4          5        0
g5          3        0
合计       21        0      ← 无幻觉
```

对照 P13-5 时期的 79.2% 幻觉率，**修复彻底生效**。
