# P14 候选落点倾向（先远后近）—— 前置准备与实施记录

**日期**：2026-11-11
**用户需求（原文）**：
> 候选序列内先去当前位姿下最远的未知格内候选，再去剩下未探索的未知格内候选，
> 达到先探索出室内大致框架、再逐步补齐室内未知区域的目的。

**硬约束（用户明确）**：**只做候选序列内的排序**，不改候选生成策略
（RRT / 前沿提取一律不动），只在可用候选内重选。

---

## 1. 为什么不是"重做 8cc16a4"

历史提交 `8cc16a4` 做过一次"区域新度优先"，78 分钟后被 `1edaae8` 回滚。回滚依据
（`nw5` vs `rs5`，同物理配置只改打分）：

| 指标 | rs5 | nw5 | 变化 |
|---|---|---|---|
| 停滞中位 | 9 s | **56 s** | ×6.2 |
| PASS | 5/5 | 2/5 | — |
| 已知面积 | 159.7 m² | 144.8 m² | −14.9 |
| 接触 | 0 轮 | 1 轮（3 段） | — |

**机制**：那次的权重 `novelty_w × (2 m 未知格数)` 把车推向**远区**，而实测远区目标
69% 走不到 → 取消 → 进黑名单 → 候选池更快耗尽 → 长时间停滞。

**关键区别**：用户这次要的是**距离排序**（越远越优先），而 `8cc16a4` 是
**新度排序**（未知格多优先），两者目标不同；但**失败机制相同**（都推向远区）。
所以 P5 的可达性把关不是可选优化，而是方案能否成立的前提。

## 2. 前置阶段实测发现（推翻了方案 (A) 的原始形态）

### 2.1 未知连通分量在本世界是退化的

用 `p13s4_g1` 的真实 `map.pgm`（234×386 @5cm）统计：

| 项 | 值 |
|---|---|
| 未知格总数 | 30266（33.5%） |
| 未知连通分量数 | 150 |
| **最大分量** | **27678 格 / 69.20 m²** |
| 其余 149 个分量合计 | 6.47 m² |
| 最大分量占比 | **91.4%** |

后果（用 `cand_pool.jsonl` 实测）：

| 特征 | 拍内归一化极差（中位） | 判定 |
|---|---|---|
| `dist` 候选自身距离 | 83.4% | ✅ 可排序 |
| `u_eff` 未知格数 | 213.9% | ✅ 可排序 |
| `reg_far` 所属区域最远点距离 | **0.0%** | ❌ **无区分度** |
| `reg_cen` 所属区域质心距离 | 0.0% | ❌ 无区分度 |
| `depth` 未知厚度 | **160.9%** | ✅ 可排序 |

**结论**：方案 (A) 若按"所属区域最远点距离"排序，84.9% 的候选都是同一个数，
排序结果与改造前完全相同 —— 等于没改。

### 2.2 替代特征：未知厚度 `depth`

`depth` = 该未知格到最近**已知格**的距离（`ndimage.distance_transform_edt`）。
房间中心厚、门框/走廊处薄，天然区分"房间"与"连接处"。

- 实测：最大 3.61 m、未知区均值 0.74 m、拍内归一化极差 160.9%
- 单测 `H`：大块 0.75 m vs 小块 0.00 m

### 2.3 阶段判据 (a) 用"最远前沿距离"是噪声

第一版用 `unknown_edge_far()`（紧邻已知空闲的未知格中离车最远的距离）。
实测 90 s 内：**上涨 40 拍 / 下跌 38 拍**，单拍最大变动 1.27 m，纯随机抖动。

直接后果：90 s 内阶段切换 **3 次**（框架→补齐→框架→补齐），两阶段互相抵消，
"先远"根本跑不出来。

**改为已探明格数`known_cells()`**（单调递增）后：第二轮冒烟只在真正发现新区域时
切换（58923 → 61455，+2532 格）。

### 2.4 远目标准入阈值不能用 `corridor_hard`

第一版用 `corridor_hard = 0.92`，实测单轮否决 **35 次**，全部卡在
"实测 0.90 m vs 门槛 0.92 m"这 2 cm 差异上 —— 属于测量噪声，不是真的窄。
改用 `pass_width = 0.90`（车宽 + 2×安全余量的通行下限）后降到 **4 次**。

### 3.2 新增方法

| 方法 | 作用 |
|---|---|

| `relay_point(gx, gy)` | 沿原目标已算出路径取中继点 |
| `probe_pool(scored, raw_of)` | 候选池快照落盘 |

### 3.3 排序规则

```
补齐阶段（frame_far_first=false 或已切换）：
    sorted(items, reverse=True)          # 与改造前逐位等价
框架阶段：
    sorted(items, key=(negd, -score))    # negd = -距离，升序 = 距离降序 = 越远越优先
```

**为什么不把距离塞进第一个元素**：下游 `top.append((u - pen - risk_pen, negd, x, y))`
里 `pen`/`risk` 是百~千量级罚分，会把米级的距离彻底淹没。改排序规则、不改元组
结构，是唯一不动下游三处解包的做法。

### 3.4 框架阶段的三个配套改动

1. **不做距离折现**：`risk_discount(d) = 1/(1+(d/4.5)²)` 是单调递减的，
   和"越远越优先"方向相反。框架阶段直接取 `p = 1.0`。
2. **强制关掉 `near_first_reorder`**：它会在 ±10% 分差带内把近的候选提前。
3. **`passing` 不再按 score 排序**：保持 `top` 的距离顺序。

### 3.5 P5 远目标处理

- **(ii) 准入**：框架阶段且距离 > `far_admit_dist` 的目标，`min_w` 必须
  ≥ `pass_width`(0.90)；不过则 `continue`（**顺位到次远**，因为 `top` 本就是
  距离降序，天然实现降级）。
- **(iii) 中继降级**：框架阶段远目标被 veto 时，在迁移模式链最前面插入
  `relay` —— 沿 `path_and_width` **已算出**的那条路径取 4 m 弧长处继续走。
  路径与目标坐标严格匹配（`_last_path_goal`），防止用到上一个候选的残值。

**根因：`patch_sim_time` 的启动竞态。**

```bash
# 修复前（错误顺序）
retry_until 12 "$MGR" exploration_retreat_enabled true      # ← 先开闸
retry_until 6  "$MGR" exploration_retreat_max_distance_m 0.15  # ← 后设限
```

`retry_until` 带重试 + `timeout 4`，两次 `ros2 param set` 之间可以隔几秒。
而 `exploration_retreat_enabled` 的 manager 默认值**本来就是 True**，
所以"开闸"这一步毫无意义，真正的问题是：**从 manager 启动到设限生效之间，
它一直以 0.35 m / 0.10 m/s 的默认包络在跑**。

→ 退 0.302 m，超出探索期单窗包络 0.20 m（`evaluate.py:252` `explore_ok`）
→ `reverse_authorized=False` → `no_reverse` FAIL
→ 且退到 `min_d=0.004`，随后接触 13 次

**修复（已改 `patch_sim_time`，两轮迭代）**

第一版修法：「先关闸 → 设全部上限 → 最后再开闸」。

```bash
retry_until 12 "$MGR" exploration_retreat_enabled false      # ← 关闸
retry_until 6  "$MGR" exploration_retreat_max_distance_m 0.15
...
retry_until 6  "$MGR" exploration_retreat_enabled true       # ← 最后开闸
```

**但 `p14vR_far1` 实测证伪了它**：

```
:409  exploration_retreat_enabled=false ✗（超时）   ← 关闸失败
:421  exploration_retreat_max_distance_m=0.15 ✓     ← 12 s 之后才落地
:417  manager: waiting for startup map/costmap warm-up (2.1/8.0s)
```

`p14vR_far2` 同一句却是 `✓`。**时灵时不灵**＝manager 的参数服务在 patch 跑时
还没准备好，12 s 重试窗口不够。所以"关闸"这一步根本不能用来兜底。

第二版（当前）：把**真正起作用的那条上限**提到第一位，给足 30 s 等节点起来。

```bash
retry_until 30 "$MGR" exploration_retreat_max_distance_m 0.15   # ← 第一条，等节点
retry_until 6  "$MGR" exploration_retreat_speed_mps 0.05
retry_until 6  "$MGR" exploration_retreat_max_sec 2.0
retry_until 6  "$MGR" exploration_retreat_rear_margin_m 0.25
retry_until 6  "$MGR" blocked_retreat_max_per_session "$RETREAT_MAX"
retry_until 6  "$MGR" blocked_retreat_min_interval_sec "$RETREAT_IVL"
retry_until 6  "$MGR" exploration_retreat_enabled true          # ← 形式动作，放最后
```

道理：R1b 的位移上界 $=\min(\text{max\_distance\_m},\ \text{speed\_mps}\times\text{max\_sec})$。
只要 0.15 m 先落地，后面 `speed`/`max_sec` 即使还是默认的 0.10 / 3.0 也翻不出 0.15 m。
残余窗口从"12 秒级"缩到"节点应答 → 第一条 set 落地 ≈ 一次 RPC"。
`exploration_retreat_enabled` 默认本就是 True，这条只是让日志可读，放最后不再承担安全职责。

##### 失败 A：`base09` —— 状态机死锁（阻塞 293 拍）

| 项 | 数据 |
|---|---|
| 结束位置 | `(8.263, -8.293)`，距原点 **11.71 m**（房子最远端） |
| 前向障碍 | **0.506–0.516 m**，持续不恢复 |
| `mode` / `state` | `safety_stop` / `blocked_waiting_clearance`，**卡 293 拍** |
| `cmd_vel` | 恒为 `(0.0, 0.0)` —— 车完全静止，无自救能力 |
| supervisor | `giveup_40s` **4 次**（每次试 41 s 后放弃） |
| manager | `front obstacle too close: 0.51m; retrying return-home 3/3` → `failed after 3 retries` |
| `session_driver` | 重发 `set_mapping_done` **10 次**，每次都被 `mapping already marked done; return-home state: blocked_waiting_clearance` 拒回 |

**根因链**：

1. `front_stop_distance` 在 launch 里被覆盖为 **0.65**（代码默认 0.40，
   `auto_mapping.launch.py:325`），加 `blocked_clearance_hysteresis_m=0.08`
   ⇒ 前门带 **0.73 m**
2. 车停在墙前 0.51 m ⇒ `0.51 < 0.73` ⇒ `front_blocked=True` ⇒ `safety_stop`
3. `return_home_retreat_enabled=false` **且** `return_home_failure_retreat_enabled=false`
   （均由 `patch_sim_time` 显式关闭）⇒ 返航倒车两条路径全禁用
4. `escape_supervisor` 的脱困靠"转向 + 前进"，而前进被前向门挡住
   ⇒ 41 s 后 `giveup_40s`
5. manager 在 `blocked_waiting_clearance` 下拒绝发起返航目标
   ⇒ 3 次重试打满 ⇒ 永久卡死

**关键矛盾（设计层面）**：车体外接半径 **0.397 m**，而实际前向净空 **0.51 m**
—— 物理上**完全不接触**，但 0.65 m 的门带判定为"堵死"。
**安全门比车的实际尺寸苛刻 64%**，在此形成"系统认为不能动、其实能动"的死锁。

`executing` 既不在 `_RETURN_HOME_STATES` 里、也不以 `return_home_` 开头
⇒ 状态守卫放行 ⇒ "返航未启动"重发 3 次 ⇒ `cancel-all` ×2 ⇒
**把正在执行的导航目标砍掉** ⇒ `return-home goal was canceled` + `status 6`。

这直接违背用户硬要求：
> 返航前必须要确认是否有导航任务，若有，则等待此轮导航结束、到点后才开始返航，
> 而不是中断正在进行的任务。

**修**：不再靠状态字符串枚举（manager 有几十个态，"正在执行目标"与状态名并不
一一对应，枚举永远会漏），改用 manager 已发布的布尔量 `nav_goal_active`
（`manager.py:2761`，1 Hz 状态 JSON）。加两道：
1. 兜底重发的条件里加 `and not _nav_goal_active`；
2. `_cancel_all_goals()` 入口再查一次，`nav_goal_active=True` 时直接拒绝并告警。

> 教训：**"不中断进行中任务"这种硬语义，必须挂在能直接表达它的信号上**
> （`nav_goal_active` boolean），而不是靠对状态机名字的猜测。状态名字会变、
> 会新增，boolean 不会。

## 2026-11-15（U）：s4manual 长驻留诊断 + 前向视觉盲区修正

### 一、长驻留：候选被同一门槛批量拒光（非卡死、非返航）

`s4manual`（900 s 手动轮）551 拍，两处长时间驻留：

| 时段 | 时长 | 位置 | 状态 |
|---|---|---|---|
| 234–321 s | **86 s** | (7.49, 4.24) | `waiting_for_rrt_frontier` |
| 368–469 s | **96 s** | (8.23, −7.34) | `waiting_for_rrt_frontier` |

两处都不是车卡住，而是**等不到可派发候选**。拒绝统计：

```
前向净空预检否决：实测 0.00m < 下限 0.58m      ← 全轮 425 次
RRT frontier rejected: no safe projection       ← 44 次
本轮候选全部被拒：rejected_size=86 rejected_path=51
                  rejected_narrow=202 reject_narrow_hard=373 published=12
```

**根因是两套口径不一致**：

| 环节 | 用哪张图 | 结论 |
|---|---|---|
| 可达性 BFS（`path_and_width`） | costmap（`data < 90`） | 能过 |
| 宽度 `min_w`（`clearance_field`） | `/map` ∪ **视觉障碍栅格(==100)** | 堵死 |

`min_w = 0.00` 的算术来源：`reach()` 从 `ks = arange(1, K+1)` 采样，第一个采样点
（5 cm）就撞到障碍 ⇒ `first = 0`。而被判为"障碍"的 425 次里，主体是**视觉层点云**
而非雷达实测的墙。

### 二、修正（方案 b）：视觉独有窄缝 → 罚分而非硬拒

`frontier_arbiter` 新增：
- `map_only_field()`——只用 `/map`、不含视觉障碍的距离场（按 `_map_seq` 缓存）
- `_narrow_is_vision_only()`——用同一条路径、只换距离场重测最小净宽
- 参数 `vision_narrow_soft`（默认 true，设 false 回到旧行为）
- 统计键 `narrow_vision_soft`

新语义：

| 情形 | 处理 | 安全性 |
|---|---|---|
| `/map` 也说窄（`min_w_map < narrow_floor`） | **仍硬拒** | 不变 |
| 只有视觉层说窄 | `_last_path_soft = 2.0` 罚分放行 | 交给 risk_route 排序 |

复核是**惰性**的：只在"本来就要硬拒"的分支里做，正常候选零额外开销。

实测验证（`p14x1_cov`）：
```
视觉独有窄缝（/map 净宽 1.05m >= 0.58m，融合场 0.25m）目标 (7.10,-3.78)：降级为罚分放行
视觉独有窄缝（/map 净宽 0.90m >= 0.58m，融合场 0.10m）目标 (8.06,-3.92)：降级为罚分放行
```
`/map` 说 1.05 m 宽，视觉层判成 0.25 m —— 证实过拒真实存在。

### 三、覆盖率终止：从"未启用"到默认启用

`s4manual` 的启动日志写明 `终止判据=定时器 900s（覆盖率终止未启用）`，
而 `known_total` 在 **180 s 已达 49080 格（99.4%）**，之后 720 s 只多探 283 格
（0.6%）⇒ 约 80% 轮次时间被浪费。

**不能只下调 threshold**：早期 `ncr_interior` 虚高（分母只统计"从当前位置可达
的未知"，其余房间被墙隔开不计入）——实测 t=15s 为 0.9903、t=60s 为 0.9988，
而 t=120s 回落到 0.9515。若 `min_explore_sec` 仍是 60 s，60 s 就会误终止。

所以三件事一起做，**threshold 保持 0.97 不动**：

| 参数 | 旧 | 新 | 依据 |
|---|---|---|---|
| `coverage_min_explore_sec` | 60 | **150** | 120 s 实测 0.9515 < θ，150 s 起 0.9718 > θ |
| `coverage_min_known_cells` | 0 | **48500** | 直接锚定"地图基本收盘"；本图 known 收敛 ≈49400 |
| `coverage_terminate`（driver） | false | **true** | 本轮浪费 720 s 的直接原因 |

⚠ `48500` 与本房型地图尺度绑定，换房型/换分辨率须按 `known` 收敛值的 ≈98% 重算。
设太高会导致永不触发（退化成只看 `explore_watchdog`）。

安全性：`coverage_auto_terminate` 仍为 False ⇒ manager 只发布 `/exploration_coverage`，
不会自己调 `set_mapping_done`；是否终止由上层决定，**实车不会自己停车**。

实测（`p14x1_cov` 第 1 轮）：`elapsed=156 s` 达标（`ncr_interior=0.9800`），
整轮 211 s，**比定时器省 689 s（76%）**，返航成功、接触 0。

### 五、修正：去掉前向视觉盲区 `range_min`（0.25 → 0.0）

**一、相机不会拍到车体（数值验证，非推测）**

相机光心 (x=0.24, y=0, z=0.26)、rpy=0 水平朝前、水平 FOV 60°、
图 160×120（垂直半 FOV 23.4°）、clip near=0.08。

| 部件 | 需要距离 | 实际 | 结论 |
|---|---|---|---|
| 底盘顶面 z=0.14 | ≥0.277 m | 车体前缘仅距相机 0.05 m | 看不到 |
| 车轮顶 z=0.20 | ≥0.139 m | 轮子在相机**后方** 0.24 m | 不在前方视野 |
| 相机外壳 x∈[−0.025, 0] | — | 全在光心后方 | 不在视野 |

且 near=0.08 处下视野边缘 z=0.225，远高于车体顶面 0.14。
⇒ 自过滤完全可由 `self_filter_shape=rect` 的精确包络矩形承担。

**二、0.25 还制造了一个反向危害**

`publish_free_rays()` 用 `(r >= range_min)` 筛回波定射线长度。当障碍真实距离
< range_min 时，该角度被判"无回波"，射线长度退回 `free_max`：

| range_min | 回波 r | 射线端点 | 后果 |
|---|---|---|---|
| 0.25 | 0.15 | **4.95 m** | 冲过障碍，把该方向视觉障碍格**清掉** |
| 0.00 | 0.15 | 0.10 m | 止于障碍前，不清障 |

即**车越贴近障碍，视觉层越会把障碍抹掉** —— 与需求正好相反。

**三、影响面**：包络矩形是 x∈[−0.17,0.30]、|y|<0.24；矩形外且 dist<0.25 的只剩
两条窄带（车正后方 x∈[−0.25,−0.17]、车两侧 |y|∈[0.24,0.25]），合计约 0.03 m²。
⇒ 这次**不是**放松安全边界，而是把一处无依据的盲区收回到精确几何上。

回退：`range_min:=0.25`。
