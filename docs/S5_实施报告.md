## M1 遗留矛盾的结论（S5 §3 M1 要求逐项给出结论）

### 1. `narrow_floor` 注释里的"车宽 0.40 / 两侧各 0.09" —— 改注释，不改数值

- 数值 0.58 对；两个因子都错：真车宽 **0.470**，真余量 **0.055**。
- `0.470 + 2×0.055 = 0.58` ✓
- 已改的位置：`launch/sim_explore.launch.py` 的 `narrow_floor` description、
  `frontier_arbiter` 的 S3 注释块、profile YAML 的备注。
- **数值未动**：改数值会让 S3 的 A/B 结论失效。

### 2. `collision_radius_m`(0.370) 与 `circumscribed_radius_m`(0.397) 并存 —— 故意的

用两个字段名区分，并在 `profile.py` 模块 docstring 写清理由：

- `circumscribed_radius_m` = 0.397 = **规划口径**（Nav2 footprint 外接圆，用于膨胀）。
- `collision_radius_m` = 0.370 = **取证口径**（实测碰撞盒，用于判"是否真的碰到"）。

两者差 2.7 cm，来源是 Nav2 footprint 比碰撞盒前后各留约 2 cm 余量。
强行统一的两个方向都错：用 0.397 取证会把"差 2 cm 没碰上"判成碰上；
用 0.370 规划会让膨胀圈套不住车角。`test_robot_profile.py` D 组把这条锁住
（断言两者**不许相等**，且 gap 在 2~4 cm）。

同理 `inscribed_radius_m`(0.235) ≠ `min_origin_edge_m`(0.18)：
前者是"整块板子里能放下的最大圆"（Step 2/3 判走廊/区域装不装得下车用），
后者是 Nav2 语义的"原点到最近外廓边"（footprint 不关于原点对称，所以更小）。

### 3. `patch_sim_time` 的 `FOOTPRINT` 常量 —— 结论：**保留字面量 + 测试交叉锁定**

S5 §1.1 要求先定"是否改为从 profile 读"。结论是 **Step 1 不改**，理由：

- `patch_sim_time` 是 bash 脚本，处在**启动关键路径**上，用
  `retry_until 12` 做 12 秒硬超时。为读 YAML 引入 `python3 -c` 或 `yq`
  解析，等于给这条路径加一个新的失败模式。
- 失败代价极高：footprint 没能被覆盖就会退回 yaml 的 0.400 宽，
  **正好复现物理接触的第 2 层根因**（controller 只按底盘中心判碰撞）。
- 所以改为**用测试锁定**：`test_robot_profile.py` C 组逐顶点比对
  `profile.footprint` 与 `patch_sim_time` 里的 `FOOTPRINT` 字符串。
  任何一侧改了另一侧没改，`smoke_check.sh` 第 0 段立刻红。

**这意味着 profile 目前不是"字节意义上的唯一事实源"**，而是
"唯一事实源 + 一处被测试锁定的镜像"。Step 6（多构型）时若要真正生成
footprint，必须同时解决"patch_sim_time 读 profile"的问题。

### 4. `test_no_magic_numbers.py` 为什么不能用正则扫数字

见该文件 docstring：`frontier_arbiter` 里带米/秒的数值字面量有 77 处
（超时、权重、半径、采样数），正则方案要么大量误报、要么白名单比代码还长。
改为**四条结构断言 + 冻结清单棘轮**：不禁止存量，但保证只减不增。

## B2：BFS 数据结构与共享（性能前置项，不在 S5 计划内）

### 为什么必须做

Step 0 的成本分解显示 `path_and_width` 的耗时 **97% 在 BFS**。而
`tick` 每拍最多调用 `path_and_width` `max_candidates`(=14) 次，
**每次都从零重新 BFS**。基线 tick P95 = 512 ms，使 Step 2 的
"单拍 P95 增量 ≤ 10 ms" 无法判定。

### 关键发现：budget 永远不触发

```python
budget = max(80000, w * h * 2)     # 386×239 ⇒ 184508
```

BFS 最多 pop `w*h` = 92254 次（`seen` 保证每格一次）。
**184508 > 92254**，所以 budget 在任何单次调用中都不可能触发 ——
目标不可达时 BFS 必然跑满整个可达区域。这不是缺陷（行为是对的），
但它说明"预算"并不能限制最坏情况。

### 两级优化

**第一级：数据结构（实测只有 1.43x，不够）**

`seen` + `parent` dict → 单个 `bytearray`（同时编码"已访问"与"父方向"），
`deque` of tuple → `list` of int + head 指针，索引算术代替元组解包。

| 场景 | 旧 | 新 | 加速 |
|---|---|---|---|
| 可达 dx=−21 dy=−181 | 219 ms | 119 ms | 1.85x |
| 远角 | 208 ms | 156 ms | 1.33x |
| 合计（5 场景） | 910 ms | 637 ms | **1.43x** |

**第二级：同拍共享（真正的收益）**

同一拍内 14 个候选、起点与 costmap 都不变，等于把同一棵 BFS 树跑了 14 遍。
改为**共用一棵树、按需推进到目标层**：

| 指标 | 独立 BFS | 共享 BFS | 加速 |
|---|---|---|---|
| 14 个目标（`s5p2` 真实地图） | 312 ms | 23 ms | **13.4x** |
| 14 个目标（`s5r2` 真实地图） | 326 ms | 21 ms | **15.5x** |

### 等价性依据（数学）

BFS 的展开序列由 FIFO 唯一确定：同样的入队顺序、同样的邻居顺序
(+x, −x, +y, −y) ⇒ 对任何目标 g（第 d 层），第 0..d 层的 parent 赋值
**逐位相同**。所以"跑到 g 就 break 的部分树"是"跑到更远目标的树"的**前缀**，
回溯出的路径必然一致。

### 我踩的坑（必须记录）

第一版 `ensure()` 找到目标就 `return`，**没有展开目标自身的邻居**。

后果：该目标的邻居在共享树里永久缺失（共享树不重跑），后续查询这些格
只能绕远路 —— 表现为**路径长度 57 vs 59** 这种静默漂移。
参考实现每次从零重跑，查到 g 时 g 虽未展开，但下次查 g 的邻居时 g 会被展开；
共享树必须显式补上这一步。

离线用"跑满 vs 跑满"的父树对比定位到 **127 格父树不一致**，修复后 0 格。
`harness/test_bfs_equivalence.py` 就是为锁住这条而写的（33 项断言）。

### 闸门测试

`harness/test_bfs_equivalence.py`（33 项）覆盖：

| # | 场景 |
|---|---|
| 1 | 同拍多目标共享（14 个候选共用一棵树） |
| 2 | 目标不可达（参考跑满 budget，共享树同样返 None） |
| 3 | 目标就是起点（路径为空，与原实现一致） |

**结论：**

1. B2 **没有引入接触回归** —— 同一出生点、B2 开启 3/3 全 0 接触。
2. **tick P95 改善 2.24 倍**（490 → 218 ms），max 改善 1.21 倍。
3. `b2canary` 的 5 接触是**随机波动**：出生点 `(1.4220, 4.2987)` 在历史上

   （`max_candidates=14` 的排序含随机项），单轮不能作为回归证据。
4. 顺带确认：该轮 72 条派发中只有 **2 条** `min_w < pass_width`，
   最小 0.583（`narrow_floor=0.58`，余量 3 mm）—— 这是 S3
   "能过但窄 → 大额罚分放行"的既有设计，不是 B2 引入。

> **诚实声明**：6 轮 A/B 的样本量只能排除"B2 显著提高接触率"这种大效应，
> 不能排除小幅效应。若后续 10 轮批次里 `bfs_share=true` 的接触率明显高于
> `false`，应重新评估。目前 11 轮（3+3 A/B + 金丝雀 + Step1 的 11 轮基线）
> 里只有 1 轮出现接触，与改造前 `p14vF`(1/2/0)、`p14vD_fb1`(106) 的波动
> 量级一致。

### 顺带发现的既有缺陷（与 B2 无关）

`candidate_probe.jsonl` 的 `unknown` 字段会被静默覆盖，出现 `-10268.6`
这类负值。原因：

```python
row = {..., 'unknown': None if unk is None else unk, ...}
...
row.update(cx or {})        # cx = region_complexity(...)，其 'unknown' 覆盖上面
```

`unk`（`path_and_width` 返回）本身是 `[0,1]` 的比例，计算正确
（`min_unk = n_unk / max(1.0, n_cells)`）。覆盖只影响落盘，**不影响决策**
（决策用的是 `unk` 局部变量）。建议把探针字段改名区分，但不在本次范围。

另一个待查项：该轮出现过 `min_w = 0.583`（`narrow_floor = 0.58`，
余量 3 mm）的派发。这是 S3 判断"能过但窄 → 大额罚分放行"的既有设计，
不是 B2 引入，但它与接触的相关性值得单独评估。

### 做法

不算"宽度"，改算**能不能放下车**：把 footprint 多边形沿路径扫过去，
逐位姿检查多边形内是否落进障碍格。

判碰撞用 `dist == 0`：`clearance_field()` 由
`scipy.ndimage.distance_transform_edt(~blocked)` 算出，障碍格上**精确为 0**，
相邻自由格为 1 格。所以"多边形内存在 `dist==0` 的格" ⟺ "多边形与障碍重叠"。
不需要第二张占据掩码，也没有浮点误判。

构型无关性（S5 §3 M2）：同一份代码换 profile 就服务三种构型。
差速/全向的直线扫掠已实现；阿克曼的弧线采样留了接口位，按 S5 §6 R3
只允许在 Step 6 实现。

### 其它两个设计决定

**超预算记为「未知」而不是「能过」**
内核为安全默认 `clear=True`（不否决），但落盘必须如实记 `swept_clear=None`，
否则后面算"扫掠误杀率"会把没算完的当成通过。

**碰撞归因（`swept_cause`）**
扫掠的障碍集合是 `/map` 占据 ∪ 视觉障碍，而 `min_w` 用的是 `/map` 单独一张。
若扫掠报碰撞而 `min_w` 很宽，必须能分辨是哪一类障碍 —— 否则"误杀率"会被
视觉层的陈旧累积污染。所以在失败位姿上重算一次 footprint 覆盖的格，
分别查两张图，落盘 `map_obstacle` / `vision_or_other`。

#### 第一版实测：不达标，且暴露了两个我自己的缺陷

| `sw2` | 开 | PASS | 0 (0/0) | ✓ | 244.9 |
| `sw3` | 开 | PASS | 0 (0/0) | ✓ | 247.4 |

| `off2` | 关 | PASS | 0 (0/0) | ✓ | 180.3 |
| `off3` | 关 | PASS | 0 (0/0) | ✓ | 211.2 |

| 组 | 通过 | 接触合计 | P95 中位（全部拍） | P95 中位（仅活跃拍） |
|---|---|---|---|---|
| 影子开 | 2/3 | **3** | 244.9 | 276.4 |
| 影子关 | 2/3 | **202** | 180.3 | 244.9 |
| **增量** | — | — | **+64.7 ms** | **+31.4 ms** |

**关于两个 FAIL 轮，必须先说清楚归因：**

- `off1`（影子**关**）是更严重的那一轮：`202` 次接触、返航失败。
  但读 `probe.jsonl` 才能看清 —— 机器人从 sim≈175 卡在
  `(2.23, 5.86)`，`mode=stopped / return_home_failed_waiting_manual`。
  之后 103.5 s 完全静止，而接触计数器是**每帧累加**的
  （43→52→66→116→145），不是"撞了 145 次"。
  **真实事件是：返航途中 1 次卡死，之后一直贴着墙。**
- `sw1`（影子**开**）3 次接触全在轮子上，单次 episode、2.0 s，
  与 §7.3 第三层记录的「manager 扫描扇区 103°–149° 盲区」特征一致。

既然**关着影子也会 FAIL 且严重得多**，"影子导致接触"就被证伪了。
（但 n=3 只能排除大效应，排除不了小效应 —— 与 B2 金丝雀同样的诚实边界。）

**为什么 +31 ms 不能作数 —— 统计口径有混淆**

两次运行的**轨迹本身不同**，于是每活跃拍的 `path_and_width` 调用数不同：
影子组 9.69 / 10.34 / 12.96，关闭组 8.00 / 8.77 / 8.27，差 **20–60%**。
P95 差异里很大一部分是"这一轮本来就干了更多活"，不是影子花的。
拿两个不同轨迹的 P95 相减，口径不成立。

**顺着 +31 ms 查到两个真缺陷（都是我写的）**

1. `sweep_top_n=8` **只在启动日志里出现过，代码里从未参与任何限制**
   （`grep sweep_top_n` 只有声明和日志各一处）。声称"每拍最多 8 次"是假的。
2. `sweep_budget_ms=30` 直接透传给 `sweep_path()`，是**单次调用**上限，
   不是每拍上限。而 `probe_candidate()` 每拍最多被调 `max_candidates`(=14) 次
   ⇒ 每拍最坏 `14 × 30 = 420 ms`。

修法：
- 预算改成**按拍共享的毫秒池**（用 `_tick_ms_n` 作拍号，翻拍即重置），
  每次扫掠后从池里扣**真实耗时**（超预算那次也扣）。
- `sweep_top_n` 真正生效：`_sweep_tick_n >= sweep_top_n` 即拒。
- 传给内核的是**剩余额度** `self._sweep_ms_left`，不是每拍全量。
- 默认预算改 `30.0 → 8.0`：验收是"≤ 10 ms"，若每拍预算本身大于 10 ms，
  这条验收**在原理上就不可能达成**。留 2 ms 给导入/配对杂项。
- 计数器全部落盘（`sweep_calls` / `sweep_skipped_quota` /
  `sweep_ms_prev` / `sweep_ms_sum`），否则"配额有没有生效"事后无法验证。

**并且把测量口径也改了**

既然跨轮 P95 相减有混淆，改成**直接测影子自己花了多少毫秒**
（`_sweep_ms_tick` 在 `finally` 的拍边界快照成 `sweep_ms_tick_prev`，
与 `tick_ms_prev` 同拍对齐）。这才是"单拍增量"的无混淆定义 ——
不需要跑影子开/关两组，也不需要两次运行的轨迹一样。

**回归锁**：`test_K_sweep_quota`（10 项断言）钉住上述全部要点，
其中关键一条是"`sweep_top_n` 必须出现在比较里"而不是"被声明"——
第一版正是因为只断言了声明，所以测试全绿而 bug 在线。

|---|---|---|---|---|---|---|---|---|
| `sw1` | PASS | **0** | ✓ | 171 | 261.6 | **2.47** | 11.41 | 74.4 ms |
| `sw2` | **FAIL** | **0** | ✗ | 450 | 184.9 | **0.54** | 9.11 | 74.7 ms |

口径说明：这里用的是**影子自身耗时**（`sweep_ms_prev`），不是"开/关两轮 P95 相减"。

### 验收 ①：影子数据可用性（能否支撑「扫掠口径切换」这个决定）

三批共 235 条候选记录，其中带扫掠结论 58 条（覆盖率 24.7%）。覆盖率低的
原因不是缺陷，是设计：同一拍里 `path_and_width` 被调用 10~13 次，
只有最后一次的路径能跟候选配对（见上文 `_last_path_goal` 配对），

| 指标 | 数值 |
|---|---|
| 有效扫掠记录 | 58 |
| 超预算（记 `None`，不计入统计） | 12（20.7%） |
| 与轴向口径**结论相反** | **33（56.9%）** |
| 扫掠判"过不去"时轴向 `min_w` | 0.90 – 1.15 m（中位 0.90） |

**56.9% 的分歧率本身是重要信号**：两套口径在同一批候选上的通过集合差异过半，
说明"轴向法向测宽"确实不是一个可靠的通过性判据。这正是 Step 2 要解决的问题。

#### 归因数据作废 —— 又是我自己的缺陷

第一版 `_sweep_cause()` 里写着 `yaw = 0.0`（注释还自我安慰"只影响归因不影响
判据"）。归因时用**轴对齐**矩形去查图，而实际失败位姿是旋转过的，查到的格
可能压根不在车体上。

这解释了一个反常现象：**33/33 条分歧全部报 `vision_or_other`**，
而对应 `min_w` 高达 0.90–1.15 m。100% 单一归因 + 反直觉的宽度，
是"归因函数本身坏了"的典型特征，不是"视觉层真的在误报"。

修法：
- 内核 `SweepResult` 增加 `at_pose`，把失败位姿的 **(x, y, yaw)** 一起带回；
  原 `at_index` 实际存的是坐标、`poses` 实际存的是数量（命名都误导，已加注）。
- 归因改用真实 yaw。
- 内点判据改为复用内核的 `point_in_polygon()`（内部走 `_row_spans`），
  与碰撞检测**同一套**扫描线 —— 否则归因结论与碰撞结论会自相矛盾。
- 归因细分为 `map_obstacle` / `vision_obstacle` / `unknown_blocked` / `other`。

#### 离线回放：**不能**确认"视觉是主因"

用最终保存的 `map.pgm` + `vision_grid.pgm`，对 33 条失败位姿做 36 朝向的
footprint 覆盖检查（任一朝向压到某类障碍即归给该类）：

| 轮次 | 扫掠判失败 | map | vision | unknown | 都不命中 |
|---|---|---|---|---|---|
| `sw1` | 5 | 0 | 4 | 0 | 1 |
| `sw2` | 19 | 4 | 0 | 15 | 0 |
| `sw3` | 9 | 3 | 0 | 0 | 6 |
| **合计** | 33 | **7** | **4** | **15** | **7** |

**这个结果与"33/33 视觉"完全矛盾，所以那个数字必须作废。**

但这次回放也**不能**反过来当结论，因为它有明确的方法学限制：

1. 回放用的是**最终快照**，而运行时用的是**当时的** `/map` 与视觉栅格。
   `/map` 会随建图增长，视觉栅格有 `vision_accum_decay_sec=120` 的衰减，
   中途存在的视觉障碍到轮次结束可能已经消失。
2. 所以"unknown 15 / 都不命中 7"这两类，很可能只是

（a）两套口径分歧率 56.9%，确实值得切；（b）归因到底该怪哪一层，还不知道。

### 逐拍 P95 不代表"卡顿可接受"

`tick` P95 ≈ 500 ms 意味着**每 20 拍有 1 拍超过半秒**，而
`frontier_arbiter` 是单线程 `rclpy.spin(node)`，那半秒内该进程的所有回调
（地图、里程计、状态）都在排队。`max` 仍可达 1.6 s。
这是 B1 之后**已知未解决**的性能问题（瓶颈是 BFS，见 Step 0 的成本分解）。
Step 2 的"单拍 P95 增量 ≤ 10 ms"在这个基线上无法判定，必须先做 **B2**。

### `s5p2` FAIL 的归因（结论：与 Step 1 无关，是既有缺陷）

日志原文（车端 `manager.current_start_is_map_clear()`）：

```
return-home delayed: current pose is too close to occupied /map cells
  → retrying return-home 1/3, 2/3, 3/3
  → return-home failed after 3 retries, keeping launch alive for manual takeover
```

两条独立证据说明不是 Step 1 引入的：

1. **取值逐位相同**（见上表，`pass_width`/`narrow_floor` 差 0.0），且这两个量
   只影响探索期候选的净宽判据，与返航起点净空判据无任何耦合。
2. **同一失败模式在改造前就存在**：`grep -c "too close to occupied"`
   在 `p14vD_fb1`（4 次）、`p14vE_sw1`（12 次，FAIL）、`p14v6_ab`（12 次，PASS）、
   `p14vH_rh1`（6 次，PASS）、`p14vJ_st1`（2 次，PASS）、`p14vG_fp2`（1 次，PASS）
   都出现过。

实测的触发链（`s5p2`）：

| sim | 事件 |
|---|---|
| 112.8 | 近距告警，位姿 (6.35, −9.67) |
| 113~164 | 只再移动 0.2 m，几乎原地不动 |

> （包络沿用 `escape_supervisor` 的 `body_sweep_clear()`），要么允许"先在
> 1.5 m 内找一个净空达标的中继点再起返航"。**本次未改**（超出 S5 范围，

### 我曾误判"取证地图与轨迹坐标系不一致"（已自我纠正，保留记录）

排查 `s5p2` 时我先得出"`map.pgm` 与 `timeline.jsonl` 完全对不上、449 个轨迹点

拟合结果（平移 0.849 / 加 180° 旋转 0.911，都不收敛）。按正确语义重算：

| 轮次 | 轨迹点数 | 落自由 | 落未知 | 落占据 |
|---|---|---|---|---|
| `s5b1..5` | 196/183/176/189/169 | **全部** | 0 | 0/0/0/1/0 |
| `s5s1` | 169 | **169** | 0 | 0 |

### `s5p2` 终点净空：manager 判据与离线复算不可直接比较（两个坐标系）

用正确语义重算 `s5p2` 的 `/map` 净空（到最近占据格的距离）：

| 位置 | 坐标（`/odom_combined` 帧） | `/map` 净空 |
|---|---|---|
| 起点 | (0.00, 0.00) | 1.100 m |
| sim=82 | (6.47, −5.38) | 1.005 m |
| sim=125 | (6.22, −9.73) | 0.702 m |
| 终点 | (6.33, −9.46) | **0.850 m** |

车端要求 `return_home_start_clearance = 0.40 m`，外接半径 0.370 m。
**0.850 m 明显达标，但 manager 仍判失败** —— 因为两者不在同一坐标系：

| 谁 | 用哪个帧 | 来源 |
|---|---|---|
| `frontier_arbiter` 的 `timeline.jsonl` / `probe.jsonl` | `/odom_combined` | `on_odom()` 直接取消息 |
| 车端 `manager.current_start_is_map_clear()` | `map` | `TF map → base_footprint` |

Cartographer 在 `finish_trajectory` 前会做最终优化，`map → odom_combined`
可能产生非零平移/旋转；机器人又已经跑到离原点 11.4 m，漂移被放大。
因此 manager 在 **map 帧**里看到的位置大概率不是我离线算的那个点，
它判"太近"**可能是对的**。

> 结论修正：`s5p2` 的失败**不是**坐标 bug，而是
> ① 探索把车带进了 map 帧下的狭窄位置，② 该分支**没有任何恢复路径**
> （见上一小节）——②才是真缺陷。
>
> 遗留：需要用在线 TF 确认 `map → odom_combined` 在返航时刻的实际偏移量。
> 离线无法补，这一项**未验证**。

> **2026-11-14 补充：这条"坐标系不同"的说明，也解释了 `p14vP_sw2` 的复现失败。**
>
> 前面 Step 2 里我写过"`sw2` 的 (6.244, -10.022) 在终局地图上净空 0.576 m，
> 按理应通过，但我无法复现"。根因就是这里：我拿 `timeline.jsonl` 的
> `/odom_combined` 坐标，去查 `map` 帧的 `/map` —— 两个帧之间可能有
> 非零平移旋转。所以那个 0.576 m **不能用来反驳 manager 的判据**。
>
> 要真正确认，只有两条路：① 录下返航时刻的 `map → base_footprint` TF；
> ② 让 manager 在报错时把 `(map 帧 x, y)` 与命中的占据格坐标一起打进日志。
> 前者要改 harness，后者要改 manager —— 都还没做。
